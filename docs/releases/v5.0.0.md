# Agent Hive v5.0.0

Released: 2026-10-15

Agent Hive v5.0.0 runs on both OpenCode hosts from one `oc-arkive` package. The v1 entry keeps its host floor of 1.18.30, and a new native v2 entry is qualified on OpenCode 2.0.26. Releases through 4.2.0 are v1-only. The v2 qualification covers 2.0.26 and makes no claim about later v2 releases.

On v1, tools, agents and permissions work as they did in 4.2.0. The v1 changes are the package dependencies, which apply to every installation, the verification-planning skills, and a `hive_git_snapshot` fix. On v2, Hive registers the same tools, commands, agents and skills, keeps your native configuration in charge of what it owns, and enforces role authority itself before any effect. The two hosts share plans, tasks and other domain state in `.hive/`, but each keeps its own native session and background records.

## Install

**OpenCode v1.** Keep `oc-arkive@latest` in the `plugin` array, or pin `oc-arkive@5.0.0`, and restart the process that hosts the plugin.

**OpenCode v2.** Install the package with npm into a dedicated directory and point the v2 `plugins` entry at its installed `dist` directory:

```bash
mkdir -p /absolute/install
cd /absolute/install
npm install oc-arkive@5.0.0
```

```json
{
  "plugins": [
    { "package": "/absolute/install/node_modules/oc-arkive/dist", "options": { "readTransport": "direct", "server": { "url": "http://127.0.0.1:4096", "passwordEnv": "OPENCODE_SERVER_PASSWORD" } } }
  ],
  "experimental": { "subagent_depth": 2 }
}
```

The [plugin README](https://github.com/imarshallwidjaja/agent-hive/blob/v5.0.0/packages/opencode-hive/README.md#opencode-v2) explains each option, how to start the server and connect the CLI, and how to pack a checkout for contributor use.

## Package dependencies

`oc-arkive` now declares `@opencode/plugin` 2.0.26, `@opencode/client` 2.0.26 and `@types/json-schema` 7.0.15 as required dependencies, because its public type declarations import them. `effect` (`>=4.0.0-rc.112 <5`) joins `@opencode-ai/plugin` as a peer dependency: a v1 host resolves the package's one eager `effect` import from the peer, and a v2 host supplies its own copy. npm 7 and later installs peers during an ordinary install. Setups that turn that off, for example with `--legacy-peer-deps`, must provide `effect` themselves.

The plugin entry and the standalone reader at `oc-arkive/dist/v2/client.js` type-check after a plain install with `skipLibCheck` off, under both NodeNext and Bundler module resolution.

## What runs on v2

The v2 entry registers all 37 Hive tools and 11 commands, dedicated and unified agent modes, custom agents, packaged skills, native dispatch and background observation, and the forensic trace and recovery tools.

### Your configuration and Hive's guards

Hive does not rewrite v2 configuration. Your settings for the default agent, an agent's description, mode, hidden state, model and variant, step limits and permission rules take precedence over Hive's registrations. Hive adds each role's instructions at request time, to ordinary turns and to compaction and generate requests. An agent with its own system prompt keeps it, followed by the Hive instructions. Commands render against your live agent catalog, and skill guidance follows your live skill catalog, preferring a unique user skill over a bundled skill with the same name.

Authority is checked when an operation runs. Every Hive executor and the native `execute.before` hook look at the agent's base role and the session's actual parent. A permission rule that makes a tool visible does not grant a role a Hive operation it lacks, a primary-only operation or `question` in a child session, edits for a read-only role, or delegation outside the role's targets. Native `general` and `explore` get no Hive tools, and Hive roles cannot run the native worktree and session-move tools, including from Code Mode. On v1, the ordered permission rules and `experimental.primary_tools` denials work as before.

### Read transport and the session-history reader

`readTransport: "codemode"`, the default, runs `hive_repositories_status`, `hive_git_snapshot` and `hive_task_trace_content` inside Code Mode, which needs the `execute` tool. Choose `readTransport: "direct"` when your permissions deny `execute`. Otherwise Hive reports the unavailable reads and logs a setup warning without lifting the denial.

The `server` option gives Hive's own reader the running server's URL and the name of the environment variable that holds its password. The password never goes into configuration. Every read is bracketed by a check that the server answers with this activation's identity for this directory, so a result read across a server restart, reload or port takeover is discarded. Hive never guesses a port or starts a server. The option configures only Hive's reader: the server and every connecting CLI process still need the password under `OPENCODE_PASSWORD` (or legacy `OPENCODE_SERVER_PASSWORD`) in their own environments.

### Dispatch, background work and traces

Child routes are bound before a child's prompt is admitted. Fresh dispatch, and continuation of a child already bound to a compatible parent snapshot, need no reader. Adopting an existing native direct child whose Hive binding is missing or has no parent, or changing a continuation's route, constraints or agent, needs the `server` reader, because Hive checks native parent ancestry and confirms the child is idle first.

Background tools and guidance are available wherever v2 supports native background subagents, without v1's experiment variable. On v2.0.26, a native completion notification carries no launching call ID. Every matching board row, even a single one, therefore stays `unknown` with the native outcome as a diagnostic, and terminal reconciliation is refused; inspect the child, then ignore the exact canonical alias. A same-process reload makes old observations uncertain and a restart makes them stale. Board state never authorizes dispatch, a replacement writer or continuation.

`hive_task_trace` and `hive_task_trace_content` share their guarded forensic index and semantic recovery across both hosts, with verified paged reads on v2. Ordinary v2 trace reads stop with the calling invocation, and recovery cancels with its caller on both hosts. Summarizer cleanup runs on independent bounded deadlines. A summarizer session created after the 10-second cleanup window can leave a known, unconfirmed ID, and there is no later sweeper.

## Separate native state

Each host owns its native records. OpenCode v1 keeps `.hive/sessions.json`, `.hive/background-jobs.json` and the feature-local `sessions.json`. OpenCode v2 uses `.hive/runtime/opencode-v2/sessions.json`, `.hive/runtime/opencode-v2/background-jobs.json` and `runtime/opencode-v2/sessions.json` inside the feature directory. A missing v2 store starts empty and never imports v1 records, and the same session ID or job alias in the two stores is two different records.

Plans, tasks, reports, handoffs, managed context, feature constraints, repository metadata and worktree registrations stay shared. On v2, Hive keeps that state in the project checkout the host resolves, so a session opened in a subdirectory, or in a Hive task worktree, uses the main checkout's `.hive`.

The VS Code companion reads both hosts' stores. Background Jobs marks v2 rows `OpenCode v2`, the constraints inspector lists each host's sessions separately, every open and archive action targets its own host's store, and an unreadable board or registry is reported without hiding the other.

## Host-aware prompts and skills

One canonical policy is rendered for each host. A host profile supplies the native subagent call (`task()` with `subagent_type` and `task_id` on v1, `subagent()` with `agent` and `sessionID` on v2), the skill call, the shell tool name, the Hive read transport, and whether background subagents need an experiment variable. Packaged skills mark the sentences and examples that differ with paired `hive-host` sections, and the materializer keeps only the loading host's sections before hashing, so each host gets its own generated skill directory.

The complexity skills are invoked by name on both hosts. Ask for `complexity-review` or `complexity-audit` with the scope in ordinary prose, or mention `@complexity-review <scope>` or `@complexity-audit <scope>` in the v2 TUI. OpenCode v2.0.26 does not register skills as slash commands, and slash invocation is not verified on v1.18.30.

## Verification-efficiency planning

Plans that state an explicit verification-efficiency outcome, such as faster delivery or less repeated verification, now have to support it at the scope the outcome states. For a delivery-level outcome, `writing-plans` compares the existing and proposed schedules across initial validation, one representative correction and integration, counting preparation, queueing, execution, cleanup and repeated acceptance, and marks unmeasured costs as unknown. An explicitly local outcome, such as faster local feedback, stays local: it keeps the integration gates, needs no whole-delivery comparison, and supports no end-to-end claim without evidence. The plan reviewer blocks a plan whose schedule leaves a stated outcome unsupported or contradicted. `verification` labels each speed statement as a measured speedup, an observed elimination or a projected benefit, and `executing-plans` raises a mismatch before repeating expensive acceptance that contradicts a stated outcome. Required gates stay binding, and plans without such an outcome are unaffected.

`verification` also stops treating a new commit identity as a reason by itself to keep or discard a passing result. What matters is whether the later change reaches the tested candidate or its inputs.

## Other changes

- `hive_git_snapshot` compares changed paths with `--numstat` and `diff.autoRefreshIndex=false`, so a snapshot no longer refreshes the index of the repository it inspects or reports stale-stat false positives.
- Shared services, Zod schemas, the 31 ordinary Hive operations and role policy moved out of the v1 adapter into host-neutral modules. V1 behavior is unchanged by this refactor, which lets both entries share one implementation.
- The documentation covers installation and upgrade on both hosts, reader versus CLI authentication, native precedence and Hive's guards, host handover and rollback, and the separate stores. The design doc embeds a diagram of the [dual-host architecture](https://github.com/imarshallwidjaja/agent-hive/blob/v5.0.0/docs/diagrams/dual-host-architecture.svg), and the Operator Guide embeds one of [which state is shared and which each host owns](https://github.com/imarshallwidjaja/agent-hive/blob/v5.0.0/docs/diagrams/native-state-ownership.svg). Each diagram also ships as standalone HTML next to its SVG.
- Packaged skill text now matches the code it describes. This changes instructions only, and no runtime behavior changed:
  - `context-engineering` names the `stale_context_cursor` code that the runtime returns for a stale named-read cursor, where it listed `context_cursor_stale`.
  - `hive-config` says that OpenCode v1 creates a missing `agent_hive.json` at startup, while v2 reads it once at activation, uses the built-in defaults when the file is absent and never writes it.
  - `background-delegation` names each host's own board file, and its shared board rule refers to the active host's `background-jobs.json`.
  - `parallel-exploration`, `brainstorming` and `systematic-debugging` lose a malformed sentence and two escaped code spans. `writing-for-agents` says `disableSkills` lives only in the global `agent_hive.json`, and `adversarial-review` suggests `git --no-optional-locks status --short`.
- `systematic-debugging` ships the upstream MIT license (`LICENSE.superpowers`) and a source record in `UPSTREAM.md` for the text it keeps from obra/superpowers, naming the upstream revision the text matches.
- The unused `packages/hive-core/templates/skills/hive.md` was removed. No loader has read it since `templates.ts` was deleted, and only tests did. The recovery-step order it carried is now pinned against the shared interrupted-worker recovery prompt.

## Upgrade from v4.2.0

1. Finish or deliberately abandon live workers in the current host.
2. On v1, update the plugin entry to `oc-arkive@5.0.0` or refresh the cached `@latest` package. On v2, install the package as shown above.
3. Restart the long-lived process that loaded the plugin, such as an `opencode` TUI, an `opencode serve` process, or a service that runs one. A restart reloads whatever the configuration points at, so update the package first. Restarting a client attached to a server does not reload the server's plugin.
4. Send a new message in each session before using Hive-governed tools, and launch fresh child sessions.
5. Install `vscode-arkive.vsix` from the v5.0.0 GitHub Release with `code --install-extension ./vscode-arkive.vsix`.

To use one project on both hosts, follow [Switching OpenCode hosts and rollback](https://github.com/imarshallwidjaja/agent-hive/blob/v5.0.0/docs/OPERATOR-GUIDE.md#switching-opencode-hosts-and-rollback). In short: quiesce writers in the old host, keep the checkout and `.hive/` in place, and give each host its own native HOME/XDG config, data and cache directories. In a disposable check, sharing one home made v1.18.30 reject v2's database with `Database is not empty and has no session table`. Hive reads `agent_hive.json` from `HOME`, so copy or recreate settings such as `agentMode`, custom agents and `disableSkills` in the new home before you start the host, or reset to the defaults on purpose. Native conversations, live workers, selected routes and session constraints do not migrate, and native stores must never be copied between hosts.

## Known limits

- The pre-release qualification ran on stock v1.18.30 and v2.0.26 hosts with scripted model providers. It establishes wiring and recorded effects, not real-model judgment.
- On both hosts, the qualification loaded a package already installed with plain npm. Host-side registry resolution at first use was not part of it. Two earlier first-prompt stalls on v2 stopped before the plugin loaded, and their cause is unknown. If first use stalls before the `loading plugin` event, keep the server logs; a successful retry does not explain the stall.
- A v2 top-level session uses the explicit CLI/session model or the native configured model rather than its agent's registered model. Check the models that actually run, including recovery models.
- Custom credential environment variables may be visible to trusted shell and tool subprocesses. An environment reference keeps the secret out of project configuration but does not isolate it.
- Activation-local reservations on v2 are not an atomic fence against an external writer to the same child session.
