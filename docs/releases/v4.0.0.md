# Agent Hive v4.0.0

Released: 2026-10-07

Agent Hive v4.0.0 changes public status and background reconciliation responses, enforces role-specific tool permissions, and adds guarded approval with task sync. It also improves interrupted-worker inspection and validates composite worktree placement before Git operations. These response and permission changes make this a major upgrade from v3.0.0.

## Breaking changes

- `hive_status` exposes a single top-level `tasks` list. `feature` contains only `{ name, status, hasPlan, commentCount }`; `feature.tasks` and `feature.reviewCounts` are removed. Task folders with missing or unreadable status records appear as `status: null` with `integrity.reason` (`status_missing` or `status_unreadable`); they are never runnable and cannot satisfy dependencies.
- `hive_background_reconcile` returns a compact acknowledgement, and `hive_background_reconcile_batch` returns `{ success, results, requiresHiveStatusRefresh }`. Full job records and scheduler guidance are available through `hive_background_status`. Failed reconciliation items include `reason`, `error`, and an actionable `hint`; successful items remain archived even if another batch item fails.
- `hive_plan_approve` returns approval failures as result objects with `success: false` instead of raising a tool error, so a completed call does not prove approval. Without `sync`, the flat result's `success` reports approval; with `sync: true`, `approval.success` reports approval and `sync` reports task sync separately. Feature routing and argument schema validation can still raise tool errors.
- Hive registers ordered OpenCode `agent.permission` rules: each role denies `hive_*` before allowing its own tools. Custom agents inherit their base role's access. Native `general` and `explore` have no Hive tools, delegation, or questions. Child sessions are denied primary-only operations, including merge, cleanup, approval/sync, task creation, constraint mutation, context archive, and background-board operations. Global allow-all permissions cannot reopen these role-denied tools.
- `hive-core` removes the exported `FeatureInfo` type and `FeatureService.getInfo`. Direct consumers must obtain feature metadata and task records from their owning services.

Hive-tool permissions and native edit denials are enforced by OpenCode. Inspection-only restrictions on shell and external effects remain instruction-bound; tool access does not authorize an agent to bypass its assignment or a denied operation.

## Added and changed

- `hive_plan_approve({ expectedRevision, sync: true })` approves the reviewed plan and syncs tasks, returning separate `approval` and `sync` outcomes. Approval reports `approvalPersisted`, failure `reason`/`stage`, and the approved revision. An unchanged retry can report `alreadyApproved`; a post-sync recheck reports superseded or unverifiable approval without rolling back task writes.
- Feature and ad-hoc worktree creation return the initial inspection, including source state, destination identity, and comparison. Callers can record `expectedTarget` or `expectedTargets` from that result; later destination checkpoints remain part of the integration contract.
- Hive Helper investigates one named feature or ad-hoc question with cited evidence, including interrupted-worker traces, retained worktree state, destination drift, and runtime state. Primaries own acceptance, integration, and cleanup. Scout remains read-only retrieval; session-trace questions go to Helper. Delegated Architect retains planning authoring and a terminal layer of blocking planning/investigation helpers, returning primary-control requests to its parent.
- The packaged `hive-config` skill provides runtime layout, state ownership, read-only task/Git/session-store forensics, and configuration references. Writing skills now describe boundaries through their operational meaning and propagate the intended reader outcome into prose handoffs.
- Forager guidance limits report/handoff publication to the bound task, leaves status/summary/blocker changes to the primary, and requires owning Hive tools for state outside the assigned worktree. The assigned worktree remains the worker's writable source workspace.

## Recovery and placement fixes

- Forensic task rows and event reads expose `child_session_id` only after fresh runtime confirmation of the child and parent relationship. Foreground recovery hints are rebuilt each turn. Recovery can provide an inspect-only `evidence_only` snapshot for an idle session with unresolved records; it rechecks authorization, parent, directory, source, and runtime lifecycle after summarization. A complete summary does not prove task completion or authorize continuation.
- Composite worktree tools validate the trusted repository topology before Git touches a root. Missing composite placement manifests produce path-specific diagnostics; manifest-backed ad-hoc creation requires `repoIds`, and bulk cleanup prunes declared repositories. `hive_status.worktreeErrors` reports invalid placements while healthy worktrees remain inspectable.
- Legacy feature-worktree creation validates task status before Git operations and rejects missing, corrupt, or unrecognized records.

## Upgrade from v3.0.0

1. Finish or explicitly abandon live workers before updating the plugin. OpenCode >= 1.18.30 remains required. For upgrades from v2.5.0 or earlier, also follow the [v3.0.0 migration](https://github.com/imarshallwidjaja/agent-hive/blob/v3.0.0/docs/releases/v3.0.0.md#upgrade-from-v250).
2. Update scripts and copied instructions:
   - Read `hive_status.tasks` instead of `hive_status.feature.tasks`, and read plan comment counts from `feature.commentCount` instead of `feature.reviewCounts`. Treat `status: null` integrity entries as records requiring inspection and repair, not pending tasks. Inspect `worktreeErrors` with the documented orphan-recovery procedure and preserve invalid placements while investigating.
   - Read reconciliation acknowledgements by item. When `requiresHiveStatusRefresh` is true, call `hive_status` before dependent feature/task or merge decisions. Use `hive_background_status` for remaining board state. Follow failure hints and inspect persistence failures before retrying; a cancellation acknowledgement does not establish worker termination.
   - Treat `hive_plan_approve` as approved only when `success === true` on a call without `sync`, or `approval.success === true` on a call with `sync: true`; inspect `sync` separately. For combined approval/sync, pass the reviewed `hive_plan_read` revision as `expectedRevision`.
   - When existing pending plan tasks must pick up an amended plan's specs, pass `refreshPending: true` to the combined call or to a standalone `hive_tasks_sync`. Without it, sync leaves existing pending specs as written; started and manual tasks keep their stored records either way.
   - Retry a failed sync with `hive_tasks_sync` only while the same reviewed approval remains successful. A plan write or patch revokes approval and returns the feature to planning, so if fixing sync needs a plan edit, or approval was superseded (`approval_superseded_during_sync`) or could not be verified (`approval_verification_failed`), read and review the current revision, then approve and sync it again.
   - A failure with `reason: 'feature_metadata_write_failed'`, `stage: 'feature_metadata'`, and `approvalPersisted: true` leaves the approval marker in place, but approval did not succeed and sync was skipped. If plan content and comments are unchanged, retry `hive_plan_approve` with the same pre-approval `expectedRevision`; the retry repairs feature metadata without rewriting the marker. `hive_tasks_sync` does not repair this metadata. For other failures, inspect `approvalPersisted` and failure `stage` before retrying.
   - Record the destination identity from worktree creation's inspection and retain later inspection checkpoints. Manifest-backed ad-hoc callers must supply the owned `repoIds`.
   - Move merge, cleanup, approval/sync, and other primary-only calls out of child assignments. Use Hive Helper for read-only investigation and have the primary perform lifecycle actions with the worker's exact source pin and inspected destination identity. Send multi-step trace questions to Helper rather than Scout. Forager publishes only its own report/handoff and uses owning Hive tools for external Hive state.
   - Review custom agents and native-agent overrides against the [access matrix](https://github.com/imarshallwidjaja/agent-hive/blob/v4.0.0/packages/opencode-hive/docs/HIVE-TOOLS.md#agent-tool-access). Reserved custom IDs and stripped native permission overrides now emit warnings. Extra skills do not expand a custom agent's base-role permissions.
3. Set the OpenCode plugin entry to `oc-arkive@4.0.0` and update any cached plugin package used by your installation. Download `vscode-arkive.vsix` from the v4.0.0 GitHub Release and install it with `code --install-extension ./vscode-arkive.vsix`.
4. Restart the process that hosts the plugin. Quit and relaunch a standalone OpenCode CLI. For a long-lived server managed by `opencode.service`, restart **`opencode.service`** in its service-manager scope; restarting a client does not reload the server plugin. Confirm the host process started after the package update, then send a new message so the runtime observes the session's agent again. Launch fresh child sessions so creation-time permission denials apply. Reload VS Code after installing the companion.

Hive preserves existing plans, tasks, context, reports, and workspace files. Operators update stale copied instructions and user-authored settings themselves. See the [operator guide](https://github.com/imarshallwidjaja/agent-hive/blob/v4.0.0/docs/OPERATOR-GUIDE.md) and [tool reference](https://github.com/imarshallwidjaja/agent-hive/blob/v4.0.0/packages/opencode-hive/docs/HIVE-TOOLS.md) for current contracts.

## Release artifacts

- Root, `hive-core`, `oc-arkive`, and `vscode-arkive` manifests and the generated OpenCode plugin manifest carry version `4.0.0`. Both root lockfiles are regenerated, and the OpenCode and VS Code `hive-core` pins are exact `4.0.0` for local workspace linking.
- The release workflow publishes `oc-arkive` to npm through Trusted Publishing and attaches `vscode-arkive.vsix` to the GitHub Release, using this file as its body. Manual rehearsal builds and tests the candidate before tagging. Follow the [release guide](https://github.com/imarshallwidjaja/agent-hive/blob/v4.0.0/docs/RELEASING.md) for preparation, rehearsal, and selective tag-backed recovery.
