# Agent Hive v5.3.0

Released: 2026-11-19

Agent Hive v5.3.0 adds retained checkouts: named, long-lived branch checkouts, such as a release line beside `main`, that task and ad-hoc workers integrate into when a caller names one as their target. Merges that apply a commit now write an integration receipt, and a new checkout brief uses those receipts to report which Hive work one checkout holds relative to another. The VS Code companion gains a Repositories & Work view. The release also adds four workflow commands, the `modern-web-guidance` skill and a prune mode for `test-quality`, and fixes several worktree, publication, context and trace edge cases.

Each host now registers 49 Hive tools and 18 commands, up from 42 and 13 in v5.2.0. OpenCode support is unchanged: v1 >= 1.18.30, and v2 qualified on 2.0.26 only. The VS Code companion still requires VS Code 1.67.0 or later.

## Install and upgrade

These steps upgrade from v5.2.0. When upgrading from a release before v5.2.0, also follow the steps marked for that case, and install v5.3.0 directly without installing v5.2.0 first. The [v5.2.0 upgrade](https://github.com/imarshallwidjaja/agent-hive/blob/v5.3.0/docs/releases/v5.2.0.md#install-and-upgrade) and the [Operator Guide](https://github.com/imarshallwidjaja/agent-hive/blob/v5.3.0/docs/OPERATOR-GUIDE.md#upgrade) give the full lock and recovery procedure.

1. Finish or abandon live workers on the hosts you are upgrading. Older binaries must not execute or recover newly targeted work, so stop them before using retained checkouts or worker targets.
2. From a release before v5.2.0, stop every older OpenCode process, its workers and Git children, and every VS Code instance that can write the same project or the shared global Hive configuration in `~/.config/opencode/agent_hive.json`. Those releases predate native locking, so their hosts cannot safely share writers with v5.3.0.
3. From a release before v5.2.0, handle the legacy locks those hosts left before installing. With their writers confirmed stopped, remove only confirmed legacy state `<file>.lock` files and feature `.plan-patch.lock` directories. Keep `.hive/.operation-locks/` entries and interrupted-operation markers for guarded recovery in step 7. Keep the permanent `.hive/.locks/` anchors and the global configuration's `.hive-lock` anchor.
4. On OpenCode v1, set the plugin entry to `oc-arkive@5.3.0`, or refresh the cached `@latest` package. On v2, install the version into the dedicated directory and keep `plugins` pointed at its installed `dist` directory:

   ```bash
   cd /absolute/install
   npm install oc-arkive@5.3.0
   ```

   The [plugin README](https://github.com/imarshallwidjaja/agent-hive/blob/v5.3.0/packages/opencode-hive/README.md#opencode-v2) covers v2 options, server configuration and host setup.
5. Install `vscode-arkive.vsix` from this GitHub Release with `code --install-extension ./vscode-arkive.vsix`.
6. Start or restart the long-lived host process that loads the plugin, such as the `opencode` TUI, `opencode serve`, or its service. Restarting an attached client does not reload the server's plugin. Send a new message in each session before using Hive tools, and launch fresh child sessions.
7. From a release before v5.2.0, inspect retained operation locks and interrupted-operation markers with `hive_worktree_recover` in a primary session before any ordinary worktree mutation. Confirm every operation process has stopped and resolve any open Git operation. Then take fresh `markerDigest` and `observedStateDigest` values from a new listing, and acknowledge the exact entry with those digests and `mutatorsStopped: true`.
8. From a release before v5.2.0, update custom merge callers and copied instructions to supply `historyIntent`.

Existing untargeted state is read as before, and no migration flag is required. Untargeted workers keep their paths, branches and source pins.

## What is new

### Retained checkouts and worker targets

A retained checkout has an ID `<repoId>/<slug>`. A project without `.hive/repositories.json` has the one repository `root`. There are two kinds:

- A **managed** checkout is a linked worktree that `hive_checkout_create` makes at `.hive/checkouts/<repoId>/<slug>/`, on a new branch from `baseRef` or on an existing branch checked out nowhere else.
- A **registered** checkout is one the project already configures, recorded at its current branch by `hive_checkout_register`. Hive never creates, moves or removes it or its branch.

Each checkout has a record at `.hive/checkouts/<repoId>/<slug>.json`, and `.hive/repositories.json` does not change. `hive_checkouts_list` shows every repository with its retained checkouts and its task and ad-hoc workers, and `hive_checkout_inspect` reads one checkout, optionally with its local paths and a cleanup proposal.

A worker binds to a retained checkout only when the caller names it: `target` on `hive_task_create`, a plan task's `**Hive target**: <repoId>/<slug>` line, or `target` on `hive_adhoc_worktree_create`. An ad-hoc run can also take a `baseRef` to start from another checkout's tip while still integrating only into its bound target. Hive never picks a target from the current checkout. A targeted worker:

- is one worktree in the target's repository, on branch `hive-targeted/task/{feature}/{task}` or `hive-targeted/adhoc/{runId}`;
- reports the retained checkout as its inspection `target`, with a `targetBinding` status;
- merges with the scalar `sourceCommit` and `expectedTarget`;
- returns `TARGET_MISMATCH` without mutation when its checkout left the bound branch or its record changed or is gone, and `GIT_OPERATION_FAILED` without mutation when the checkout cannot be read.

`hive_checkout_readiness` records a primary's readiness statement pinned to the checkout's current commit, optionally naming the next destination checkout. Hive does not verify the work behind it and gates nothing on it; inspection reports `headMoved` once the checkout moves past the declared commit.

`hive_checkout_cleanup` acts on the proposal from `hive_checkout_inspect({ id, cleanup: true })` and takes its `identity` unchanged as `expectedTarget`. It refuses while an unfinished task, a targeted worker or another checkout's next-target declaration names the checkout, while a source that could name it cannot be read, or while an interrupted worktree operation guards its repository. A managed checkout must be clean and on its intended branch; ignored content is removed only with `removeIgnored: true`. The branch stays unless `deleteBranch` proves containment in another retained checkout or discards it at an exact commit. A registered checkout only loses its record.

Only Hive, Swarm and Hive Builder primary sessions change retained checkouts. Every Hive role can list them. The [retained checkout reference](https://github.com/imarshallwidjaja/agent-hive/blob/v5.3.0/packages/opencode-hive/docs/HIVE-TOOLS.md#retained-checkouts-7-tools) lists results, refusal reasons and cleanup rules.

### Integration receipts and checkout briefs

Every task or ad-hoc merge that applies a commit writes a write-once receipt at `.hive/provenance/integrations/<sha>.json` for the resulting commit. The receipt links that commit to its feature task or ad-hoc run. An ad-hoc receipt also names the run's Worklog when the host recorded one at create, and a receipt names the session and agent that called merge when the host knows them. A squash or rebase receipt lists the receipts of the commits it rewrote, so the association survives history rewriting. The host stamps the Worklog and the caller, so no tool gains an argument, and no-op merges write no receipt. A receipt's Worklog reference is a pointer: the checkout brief reports a named log it cannot read as a gap.

Receipts are advisory and gate nothing. When a merge result reports `provenance.status: "failed"`, the Git result stays and the source placement is retained. The [receipt contract](https://github.com/imarshallwidjaja/agent-hive/blob/v5.3.0/packages/opencode-hive/docs/HIVE-TOOLS.md#integration-receipts) describes when to clean up after a failed receipt.

`hive_checkout_brief({ id, against? })` is the read to take before integrating one retained checkout into another. The destination is `against`, or else the source's declared `nextTarget`; Hive never picks `main` or the project root. The brief returns ahead and behind counts, commits and changed files. It lists the receipts the source brings that the destination lacks, with each task's records or the run's Worklog header, and the receipts the destination already holds. It also lists commits no receipt covers and the gaps it could not establish. Every list has a fixed cap. The brief writes no Hive state and runs no fetch command. See [Checkout brief](https://github.com/imarshallwidjaja/agent-hive/blob/v5.3.0/packages/opencode-hive/docs/HIVE-TOOLS.md#checkout-brief).

A dispatch whose first non-empty line is `Hive task: <task-folder>` or `Hive run: <runId>` now records that task or run on the child's session record once the host reports the actual child. A task line needs a feature the parent explicitly selected and a readable task listing with a matching folder, which may be an integrity entry whose status is missing or unreadable. A run line needs a readable ad-hoc run in this project. A line Hive cannot resolve associates nothing. The association is for viewers and does not change routing or continuation rules.

### Repositories & Work in VS Code

The Tracked Repositories view is replaced by **Repositories & Work**, one tree per configured repository. Each tree shows:

- the repository checkout with its branch and commit;
- retained checkouts with their recorded readiness and next destination, for example `Ready → develop`, or `Missing`, `Unavailable` or `Off intended branch` when the checkout cannot be read as recorded;
- temporary workers nested under the checkout each is bound to, with workers whose target cannot be resolved under **Other workers / unresolved**;
- on expansion, local branches that no Hive record represents.

Unreadable records stay visible with their problem. Session and background job activity appears only when a record names the exact task or run, and ambiguous activity is shown as ambiguous. Rows offer **Open in New Window**, **Open in Terminal**, **Copy Path**, **Copy Branch Name** and **Copy Commit SHA**. The view has no merge, rebase, push, branch deletion or worktree cleanup actions.

**Remove Stale Hive Record...** on a `Missing` managed retained checkout inspects it again and lists anything that still references it. When nothing does, it deletes only the record file after one confirmation. It reads Git without changing it, so the branch and Git worktree registrations stay. See the [extension README](https://github.com/imarshallwidjaja/agent-hive/blob/v5.3.0/packages/vscode-hive/README.md#removing-a-stale-checkout-record).

### Workflow commands

Four new commands bind no agent or model and take plain-language steering after the command, like `/implement`:

- `/investigate [problem]` diagnoses from evidence and returns a proposed fix with success criteria. It changes no product code.
- `/walkthrough [subsystem or change]` explains how a subsystem works now, or what a finished change did, through the `how` skill.
- `/merge-to-main [steering]` resolves the source, the intended main destination and dirty state, and checks the selected agent's integration authority before acting. It reviews the combined result against the destination and verifies it there.
- `/handoff [next job]` writes one copyable, self-contained assignment for another agent. It dispatches nothing and records nothing.

`/test-audit [paths or natural-language scope]` routes a report-only test suite audit to `dash-reviewer` using the `test-quality` skill. `/grill` now ends by recommending the step the agreed result warrants (a direct answer, `/implement`, `/hive-plan` or `/investigate`), and both `/grill` and `/interview` close with a chronological readback of every question and answer. `/council` accepts ordinary prose: the agent selects a group only when you request one by name, and otherwise uses `council.defaultGroup`. On OpenCode v1, `/implement` now uses ordinary `$ARGUMENTS` template substitution, so special template syntax in its text is processed by the host as for other commands.

### Skills and guidance

- **`modern-web-guidance`** bundles 208 guides adapted from GoogleChrome's modern-web-guidance v1.0.0 as local Markdown, with category indexes and a codebase UI/UX audit and modernization workflow. Agents load it for UI/UX audits, frontend modernization and browser-facing web work. It makes no network calls, and its Apache-2.0 and CC-BY 4.0 notices ship with it.
- **`test-quality`** owns outcome, oracle and duplicate-coverage guidance for reviewers and audits. An explicit request to prune, rewrite or remove weak or redundant tests now enters its prune mode, which works within the named scope under the active role's implementation lifecycle. Reviews and audits stay report-only.
- **Verification** finishes a scoped change with fresh proof of what it changed and the consumers it reaches, plus required gates, without an earlier whole-product pass. `project-verification` separates reusable agent-only controls from shared tooling.
- **Writing** guidance asks for text a reader understands on the first read, with subjects that can literally do what their verbs say, sentences that end on their fact and headings that name their content. Writing skills route by the task and actual defects regardless of text length.
- **Implementation choice** is judged by fit. A simpler design that changes behavior, a contract or external dependencies is reported as a structural proposal for an operator decision, not applied as a finding.
- **Skill materialization** reuses an existing generated skill directory when its predicted digest matches, without creating a temporary staging copy.

### Fixes

- Worker create, merge and cleanup check that a worker record matches its placement, and a placement without its own record cannot take over a branch another record names. Ad-hoc cleanup no longer removes a task's worker. A create stays `createUnconfirmed` until its own checkout is confirmed, and merge refuses such a worker with `CREATE_UNCONFIRMED`.
- A failed integration counts as restored only after the target's path, branch, commit, Git operation state and tracked tree are verified; otherwise it returns `ROLLBACK_FAILED` and keeps its pending markers. Merge preflight refuses stopped revert or squash state and checkout locks.
- Approval binds to validated plan content, archived lifecycle state is preserved, and task sync and creation no longer leave phantom or partially published tasks. Failures after publication say that the feature or task exists.
- Context reads present the exact `revision` and `contentHash` guards before the content, guard errors explain malformed and mismatched values, and BOM bytes survive reads and appends.
- Session traces close complete user input steps, keep errors in order and count compactions accurately. The background board keeps notices until acknowledged and reports conflicting terminal evidence.
- `hive_feature_complete` warns about the feature's task workers that remain.

## Known limits

- The host qualification on stock v1.18.30 and v2.0.26 with scripted providers does not cover the seven retained checkout tools or the `/investigate`, `/walkthrough`, `/merge-to-main` and `/handoff` commands. OpenCode v2 qualification remains limited to 2.0.26.
- Readiness is a primary's statement, not a verification result. A receipt shows that an integration happened, not that its change is still in effect or that checks ran.
- The cleanup reference scan and the VS Code stale-record scan are not transactional against task writes. When a checkout must stay unreferenced, stop agents that could make a task name it until the removal returns.
- A Git build that predates `GIT_NO_LAZY_FETCH` can still lazy-fetch a missing object in a partial clone while the checkout brief runs.
- Native locking has been exercised on Linux x64 under Node and Bun only, as in v5.2.0.
- Instruction and skill changes are checked by wording and delivery tests. This release makes no new cross-model or cross-provider claim that models follow them.

## Release artifacts

The root, `hive-core`, `oc-arkive` and `vscode-arkive` manifests and the generated OpenCode plugin manifest carry version `5.3.0`. Both root lockfiles are regenerated, and OpenCode and VS Code pin local `hive-core` to exact `5.3.0`.

The release workflow publishes `oc-arkive` to npm and attaches `vscode-arkive.vsix` to the GitHub Release, using this file as the release body. The [release guide](https://github.com/imarshallwidjaja/agent-hive/blob/v5.3.0/docs/RELEASING.md) covers preflight, rehearsal and tag-backed recovery.
