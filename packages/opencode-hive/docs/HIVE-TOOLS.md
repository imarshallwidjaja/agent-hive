# Hive Tools Inventory

Tool availability plus instructions govern action. Each tool validates its own operation.

## Host entries and read transport

From 5.0.0, one package supplies native v1 and v2 entries, now each with all 50 tools and 18 commands. Releases through 4.2.0 are v1-only. The current source is qualified on v1.18.30 and v2.4.1; 6.0.0 was qualified on v2.3.2, and the 5.0.0 through 5.3.0 releases were qualified on v2.0.26. Installation, `plugins` options and actual model-selection semantics are in the [plugin README](../README.md#opencode-v2).

V2 registers every tool through one validating registrar. `readTransport: "codemode"` (default) sets the Code Mode flag on only nine reads, and the host then offers them only through `execute`: `hive_repositories_status`, `hive_repositories_discover`, `hive_git_snapshot`, `hive_task_trace_content`, `hive_worklog_list`, `hive_worklog_read`, `hive_checkouts_list`, `hive_checkout_brief` and `hive_explore_read`. None of them writes Hive state or is primary-only. The registrar groups them in one Code Mode namespace, `hive`, under their names without the `hive_` prefix: the host joins the two back into the same `hive_*` tool ID, so permissions, role grants and the execution guard see the usual name, and code calls `tools.hive.worklog_read`. One script can chain reads, such as `hive_checkouts_list`, then `hive_checkout_brief` for a pair, then `hive_worklog_read` for a contribution's Worklog, and return only what it needs. A read the catalog folds away is found with `search({ namespace: "hive", query: "checkout brief" })`; a search without `query` returns every Hive read with its full description. Controls, repairing reads, worktree and checkout inspections, mixed `hive_task_trace`, `hive_worklog_record` and `hive_explore_update` stay direct. `readTransport: "direct"` makes all 50 direct, outside any namespace, with the same IDs and authority. Use direct mode when global, per-role or custom-agent permissions deny `execute`. When a Hive role agent's permissions deny `execute`, Hive adds a notice to that agent's instructions naming the Code Mode reads its role is granted, logs a setup warning, and preserves the denial. Other agents get no notice; the `/worklog` and `/merge-to-main` commands name the transport of the reads they use in their own text for them.

For the 48 shared tools, both hosts deliver the same tool descriptions and argument descriptions to the model, built from one definition per operation; `hive_background_status` and `hive_background_cancel` register an `unsupported_on_host` stub on v1 and their live definitions on v2. Those descriptions explain how arguments relate, what an operation changes, what its result means and when a retry is unsafe. They do not enforce anything: the Zod argument shapes, the services and the role guards do, and this document is the reference for operators and engineers. The runtime does not read it.

The access matrix below names canonical role authority on both hosts. Its config-hook/`primary_tools` mechanism is v1-specific. On v2 native user settings own supported default selection, presentation, model/variant, limits and permission visibility. User allow rules can make a forbidden tool visible in native permission settings. On v2 `context` and `compaction` requests, Hive drops from `event.tools`, identically for both, every tool it refuses the caller for every input (`isToolUnconditionallyDenied` in `role-policy.ts`): ungranted or child-denied Hive tools, the native bypass tools, and role- or child-denied native tools. A tool refused only for some inputs, such as `subagent` for a role with delegation targets, stays. Code Mode inner tools are not listed in `event.tools`, so this pruning never removes them, and each inner call still passes through the execution guard. An unmanaged top-level agent keeps every tool. Whatever the model is offered, every Hive executor and the native `execute.before` hook still check canonical role/custom inheritance and actual child ancestry before effects. Mode/description do not grant authority; ordinary native `general`/`explore` cannot run Hive tools. The v2 `subagent()` wrapper refuses a `model` argument when the target is a Hive role or custom agent, before route capture or any native effect, and, when the target has an effective configured model, refuses a same-agent continuation unless the child's session model equals it (a model-less target inherits and is not checked; `src/v2/dispatch.ts`; operator rules in the [plugin README](../README.md#agent-models)). Request-time instructions survive user prompt configuration; user skills retain live-catalog precedence. V2 needs operator-set `experimental.subagent_depth: 2` for delegated Architect helpers.

## Agent Tool Access

On v1, Hive registers ordered `agent.permission` rules in OpenCode. Each Hive role starts with `'hive_*': 'deny'`, followed by exact allows and native permissions. OpenCode v1.18.30 appends these rules after global permissions and evaluates the last matching wildcard rule, so a global `{"*":"allow"}` cannot reopen a role-denied Hive tool. The rule also covers future `hive_*` names. Custom agents inherit their base role's permissions.

On v1, OpenCode's `experimental.primary_tools` adds session-level deny rules when native `task()` creates a child. These come after agent rules, including for delegated Architect. Hive preserves operator-supplied entries and adds `question` plus the primary-only Hive operations below. On v2, Hive refuses the same operations and `question` in any child session at execution time, whatever the native permission rules show:

- Feature control: `hive_feature_complete`, `hive_feature_select`.
- Plan/task control: `hive_plan_approve`, `hive_tasks_sync`, `hive_task_create`.
- Integration/placement: `hive_worktree_merge`, `hive_worktree_cleanup`, `hive_adhoc_worktree_create`, `hive_adhoc_worktree_merge`, `hive_adhoc_worktree_cleanup`, `hive_worktree_recover`.
- Retained checkouts: `hive_checkout_create`, `hive_checkout_register`, `hive_checkout_readiness`, `hive_checkout_cleanup`.
- Constraints/archive: `hive_constraints_add`, `hive_constraints_edit`, `hive_constraints_clear`, `hive_context_archive`.
- Live children: `hive_background_status`, `hive_background_cancel`.
- Authored records: `hive_worklog_record`, `hive_explore_update`.
- Council rosters: `hive_councils_list`. A delegated Architect returns a council request to its parent instead.

`hive_worklog_record` and `hive_explore_update` stamp the calling session as the author of shared records, so on v1 their executor also checks the caller's role grant and reads the session's live parent before writing, as the v2 guard does for every Hive tool. A broad operator allow rule or a missing `primary_tools` entry therefore cannot let a child, including delegated Architect, record, and the call is refused when the session cannot be read. `hive_councils_list` runs the same v1 check before reading: Architect's role grant includes it, and v1 writes `primary_tools` into a child only when the child is created, so a delegated Architect child created before the tool existed and later continued would otherwise have no stored deny.

Delegated Architect retains its inherited route and uses explicit feature arguments for planning. It may register discovered repositories through `hive_repositories_update`; other subagent roles' Hive allowlists exclude that tool. It returns primary-only requests (approval, sync, archive, council, placement create or cleanup) to the parent, and reports an interrupted or unresolved helper with its identity there; the parent's live child tools inspect or interrupt the delegated Architect itself, not its helpers. Its `task` permission, on primary and child sessions alike, allows one terminal layer of Scout, Investigator, plan-reviewer, approach-advisor, code-reviewer, simplicity-reviewer, vulnerability-reviewer, their custom variants, and `hive-helper`. Dispatching the code, simplicity and vulnerability reviewers only as council seats under the `council` skill is instruction-bound, not a permission, and only a primary Architect convenes: a delegated Architect lacks the primary-only `hive_councils_list`, returns a council request to its parent and does not dispatch those three reviewers; `task` is deliberately absent from `primary_tools`, and `subagent_depth: 2` supports this helper grandchild. Independent permitted calls may be emitted together, and delegated Architect waits for each helper's result before relying on it; the live child tools stay unavailable to it. Architect as primary or child routes multi-step trace/evidence questions and known identities to Helper and performs single direct spot-check reads itself. Helper is read-only and terminal, retaining inherited child-session denials. Other subagents cannot delegate or ask questions. Execution primaries can dispatch registered workers, reviewers, Architect, Helper, and ordinary native subagents, but cannot dispatch another primary or an unknown target. Architect, as primary or child, can dispatch Investigators (built-in and derived) for experiments but never implementation Foragers. Review primaries dispatch inspection-only specialists, Helper, and Investigators (built-in and derived) for runtime exercises; they cannot dispatch implementation Foragers, Architect, native `general`/`explore`, or another primary. The grant is dispatch authority only: whether a run is authorized, where it happens, and how it ends are instructions in the shared Experiments method, and Investigator returns evidence, never a patch to merge.

`hive_feature_create` stays available to delegated Architect so it can create the feature that owns its plan without changing the inherited session route.

## Feature Management (3 tools)

| Tool | Purpose |
|------|---------|
| `hive_feature_create` | Create a new feature without changing the selected session route |
| `hive_feature_complete` | Mark feature completed; return incomplete tasks and remaining task workers as warnings |
| `hive_feature_select` | Set `{ feature }` as the selected session route, or `{ feature: null }` for a featureless route |

`hive_feature_create` takes required `name` and optional `ticket`. It stages the new indexed directory and publishes it with one rename. A failure before that rename publishes nothing, so the same name can be created again. A failure after it (flushing the features directory, or releasing the feature lock) returns an error that names the created directory and says the feature exists: read it with `hive_status` and do not create it again. When `hive_feature_complete` fails with an error that says it published the new metadata, that the stored metadata matches the update, or that the update may or may not be in place, read the feature before retrying. Matching stored metadata does not show that the failed call wrote it. `hive_feature_complete` takes optional `name` and returns `{ success, feature, warnings }`. Completion warnings include missing/unreadable task status folders as incomplete entries with `status: null` and `integrity.reason` (`status_missing` or `status_unreadable`), alongside healthy tasks that are neither done nor cancelled. Completion changes only feature metadata and removes or verifies nothing. When the feature's task workers remain in the checkout inventory, a `{ remainingWorkers: { items, total } }` warning lists them as `hive_checkouts_list` does, including a worker whose checkout is gone while its branch remains (`retained.branchCommit`); the feature's workers sit in the worktree group of whichever of its names created them (the name passed, its logical name or its feature directory name). Inventory entries that could not be read in those groups, or above them such as `.hive/.worktrees` itself, add `{ worktreeErrors: { items, total } }`, and an inventory that fails adds `{ worktreeInventoryError }`. Each list holds at most 20 items. `hive_feature_select` requires `feature` (a name or `null`) and returns the updated session binding.

| Call | Effect |
|------|--------|
| `hive_feature_select({ feature })` | Set the session route used for omitted feature-scoped calls and child dispatch |
| `hive_feature_select({ feature: null })` | Make omitted calls and child dispatch explicitly featureless, suppressing detected and sole-live fallback |
| explicit `feature` or `name` on a feature-scoped tool | Target only that tool call without changing the selected session route |

Only `hive_feature_select` changes the selected route. Feature creation, explicit tool targets, and feature-task worktree lifecycle calls leave it unchanged. Create feature-task worktrees with an explicit feature target. Before native `task()` dispatch, call `hive_feature_select` only when the selected route is unset or differs from the dispatch target, or the selection evidence below is missing or uncertain. Reuse a matching selection across a same-feature batch only when this session's most recent route-changing call visible in context is `hive_feature_select` for that same feature, with no later explicit-null or other-feature selection, or, on OpenCode v2, when this session's `hive.session` session instruction entry shows that feature as the selected route; Hive keeps that entry through compaction. When neither is visible (for example at session start, in mixed ad-hoc/feature batches, or on v1 after compaction or a summary), or you are uncertain, call `hive_feature_select` for the dispatch target. Explicit null suppresses fallback and stays featureless unless the dispatch intentionally targets a feature.

## Repository Manifest (3 tools)

| Tool | Purpose |
|------|---------|
| `hive_repositories_status` | Inspect project repository mode and `.hive/repositories.json` |
| `hive_repositories_discover` | Discover in-workspace git repositories without mutating the manifest |
| `hive_repositories_update` | Add project-relative repositories to `.hive/repositories.json` atomically; matching legacy global topology is migration-only |

Status and discover take no arguments. Update requires `repositories: [{ id, path }]` and returns `configPath`, `added`, `skipped`, `repositories`, and optional legacy cleanup details. Status reports `mode` (`manifest`, `legacy-root`, or `missing-manifest`), `configPath`, `repositories`, and optional `source`/`error`; discover reports bounded `candidates` and a `truncated` flag.

Single-repo projects use the normal git-root path. Agents should add only repositories they have decided to work in. Discovery is bounded to the project root, depth 4, and 50 candidates, and skips `.git`, `.hive`, `.opencode`, `node_modules`, build outputs, coverage, and temp folders. Updates are add-only.

## Plan Management (4 tools)

| Tool | Purpose |
|------|---------|
| `hive_plan_write` | Write or replace the full plan.md for initial plans and major rewrites (execution truth; clears plan review comments and revokes approval) |
| `hive_plan_patch` | Patch bounded plan sections/tasks with `expectedRevision` from `hive_plan_read`; clears plan review comments, revokes approval, and does not sync tasks |
| `hive_plan_read` | Read plan.md and related review comments, including revision/hash; use `mode: "outline"` when full content is not needed |
| `hive_plan_approve` | Approve plan for execution |

`hive_plan_write` requires `content`, accepts optional `feature`, and returns JSON `{ path, unownedTaskHeadings? }`. `hive_plan_patch` requires `expectedRevision` and `operations`, with optional `feature`; operations use `replace_section` or `insert_after_section` with `headingPath`, or `replace_task` with `taskNumber`, and each supplies `content`. Patch returns revision, content hash, and changed sections. `hive_plan_read` accepts optional `feature` and `mode: 'full' | 'outline'` (default `full`) and returns status, comments, revision, and content hash, plus either full content or headings and task list. Full read, write, task sync, and status include `unownedTaskHeadings: [{ line, title }]` when present. Read (both modes, when a plan exists), write, patch, approval, task sync, and status also carry the advisory `planSync` described under [Plan sync status](#plan-sync-status).

Write, patch, and approval first resolve the feature to exactly one existing feature directory with readable metadata. A name that matches none, matches more than one, or matches a directory whose `feature.json` cannot be read is refused before the plan lock is taken or any file or directory is written, so a refused call leaves no feature directory behind. Reads keep their absent results: `hive_plan_read` of a feature without a plan returns `null`. A full `hive_plan_write` clears every plan review comment, as a patch does, because comments anchor to lines of the text they reviewed; there is no comment carry-over. A completed feature refuses plan writes, patches, and approval. The check runs when the call is admitted under the plan lock, and completion does not take that lock, so a call admitted just before `hive_feature_complete` can still finish after it: a write or patch then changes `plan.md` of the completed feature, and an approval reports `feature_metadata_write_failed` with `approvalPersisted: true` because completed metadata cannot be reopened. Calls admitted after completion is recorded are refused. An archived feature accepts all three and stays archived: neither approval nor revocation changes its status or archive fields.

`hive_plan_read` returns two identities. `contentHash` is the SHA-256 of the plan text alone; `revision` hashes `contentHash` together with the comments and the approval state, so a comment or an approval change moves `revision` and leaves `contentHash` as it was. Feature plan assessment (the paired `plan-reviewer` and `approach-advisor` assessments the planning and orchestrating prompts require before approval) binds to the `contentHash` the assessors read, while approval keeps passing `expectedRevision` from a fresh read. `hive_plan_approve` neither requires nor records assessments; the obligation sits with the agents.

`hive_plan_approve` accepts optional `feature`, `expectedRevision`, `sync`, `refreshPending`, and `refreshTasks`. Without `sync: true`, it returns the approval outcome directly and does not sync tasks. Success is `{ success: true, feature, approvalPersisted: true, revision, contentHash, alreadyApproved?: true }`; `revision` is the approved plan revision and `contentHash` the plan content that approval checked. A supplied `expectedRevision` guards content, comments, and approval state from `hive_plan_read`. Validation and a pre-write recheck run under the plan lock. A retry with the same pre-approval revision succeeds with `alreadyApproved: true` only when content and comments are unchanged and the approval still covers the plan. It leaves an existing successful approval unchanged and retries an incomplete metadata update. Approval and revocation update `feature.json` through the feature metadata writer, which rereads the file under its lock and keeps fields written by others.

Approval writes the `APPROVED` marker whole, as `Approved at <timestamp>` followed by `Content-SHA256: <contentHash>`. Such an approval covers only that plan content. An edit to `plan.md` made outside the plan tools leaves the marker in place but makes the plan read as unapproved (`status: 'planning'`, with the unapproved `revision`); restoring the approved bytes restores the approval, and approving the edited plan stamps its content. Hive reads the marker's whole bytes and accepts two forms. Exactly `Approved at <timestamp>\nContent-SHA256: <64 lowercase hex characters>\n` is a stamped approval. Exactly `Approved at <timestamp>\n`, with the `toISOString()` timestamp, is what every release before content stamping wrote; it still approves whatever `plan.md` holds, and an explicit approval of the current plan, including an unchanged `alreadyApproved` retry, restamps it with that content, after which an outside edit leaves the plan unapproved. Any other bytes approve nothing: an empty file, an unknown or misspelled field, a malformed hash, an extra line, a missing final newline, or CRLF line endings. Approving the current plan replaces such a marker. A damaged file whose bytes still equal one of the two forms reads as that form; the reader cannot tell it from a genuine marker. Approval flushes the marker before the rename that publishes it, so a crash does not leave an empty marker in its place. Plan writes and patches remove the marker in every form.

Approval failure is `{ success: false, reason, stage, approvalPersisted, error, revision?, metadataPublication? }`. `approvalPersisted` reports whether an approval covering the current plan exists at the failure observation; a rejected call may encounter an approval that already existed. Failure stages distinguish pre-write validation from marker and metadata writes:

| Reason | Stage | Meaning |
|--------|-------|---------|
| `expected_revision_required` | `validation` | `sync: true` needs the reviewed revision; no approval writes |
| `refresh_pending_requires_sync` | `validation` | `refreshPending` was supplied without `sync: true`; flat failure, no approval writes |
| `refresh_tasks_requires_sync` | `validation` | `refreshTasks` was supplied without `sync: true`; flat failure, no approval writes |
| `invalid_refresh_tasks` | `validation` | The `refreshTasks` selection fails the checks under [Selected task refresh](#selected-task-refresh) against the current plan and task records; no approval writes |
| `feature_unresolved` | `validation` | The feature name matches no feature, more than one, or one with unreadable metadata; nothing was written, and `approvalPersisted` is `false` because no feature was identified |
| `stale_revision`, `unresolved_comments`, `unowned_task_headings`, `plan_layout_unreadable`, `plan_missing` | `validation` | Approval rejected before writes |
| `plan_approval_failed` | `validation` | Other pre-write failure, such as a completed feature or unavailable plan lock |
| `approval_marker_write_failed` | `approval_marker` | Marker write failed; inspect persisted state before retrying |
| `feature_metadata_write_failed` | `feature_metadata` | Marker step succeeded or was already approved, but `feature.json` update failed; inspect both files. When the durable write itself failed, `metadataPublication` says what is known: `applied` (this call published the metadata, which may not survive a crash and may since have been changed by a writer outside the lock), `matches` (the stored file reads back equal to the attempted metadata, which shows the bytes, not that this call wrote them), or `unknown` (it could not be read back or differs, so the update may or may not be in place). Read the feature before retrying |
| `approval_superseded_during_sync` | `sync_verification` | Post-sync approval is absent or its revision differs from the approved revision; includes `revision` and `currentRevision` when readable |
| `approval_verification_failed` | `sync_verification` | Post-sync plan state could not be read; includes `revision` |

With `sync: true`, `expectedRevision` is required and the response is `{ approval, sync }`. Failed approval skips sync as `{ success: false, skipped: true, reason: 'approval_failed' }`, including a partial metadata failure. Successful approval runs the same `TaskService.sync` logic as `hive_tasks_sync`, with optional `refreshPending` and `refreshTasks`, bound to the approved `contentHash`: if `plan.md` changed after approval checked it, sync rejects before writing anything. Sync success is `{ success: true, created, removed, kept, manual, refreshed?, skipped?, unownedTaskHeadings? }`, and failure is `{ success: false, reason: 'task_sync_failed', stage?, applied?, interrupted?, error }` (see [Task Management](#task-management-3-tools) for the failure fields). The tool then rechecks that approval still holds and the plan revision equals the approved revision, even if sync failed. A concurrent write, patch, or comment makes the approval outcome fail explicitly while retaining the actual sync outcome. These are sequential outcomes, not a transaction; writes are not rolled back. Read `stage`, `applied`, and `interrupted` and inspect the tasks they name before retrying. When approval is still successful and the failed call selected no `refreshTasks`, address the error and retry `hive_tasks_sync`, keeping `refreshPending: true` when the call had it. When the failed call selected `refreshTasks`, fix the cause and repeat the approve-and-sync call on a freshly read and reviewed revision, because standalone sync cannot select tasks; an unchanged approval returns `alreadyApproved: true`. When approval was superseded or verification failed, read and review current state before approving and syncing again.

Inside `## Tasks`, every `###` must be `### N. Title`. Put amendments in a `####` subsection of the owning task using `replace_task`, and shared notes outside `## Tasks`. A patch that adds an unnumbered `###` there is rejected. Approval blocks while one remains or the task layout cannot be read (for example, two Tasks sections). Repair existing unnumbered headings with one `replace_section` on `headingPath: ["Tasks"]`; `replace_task` stops at the next `###` and cannot absorb an orphan heading.

If task sequencing, dependencies, or scope changed after a patch, have the primary approve and sync the reviewed revision with `refreshPending: true`. Use standalone `hive_tasks_sync({ refreshPending: true })` only while approval remains successful and sync still needs to run or retry, and only when the failed call selected no `refreshTasks`.

### Selected task refresh

`refreshPending` rewrites only pending plan tasks. To apply an amended plan to a started plan task, the primary passes its folder in `refreshTasks` on `hive_plan_approve({ expectedRevision, sync: true, refreshTasks: [...] })`; `hive_tasks_sync` does not accept the option. Selecting a folder is the primary's statement that it confirmed no assignment for the task is still running and that the task's changed scope was reconciled with its retained work. Hive does not derive either fact from task status.

A selected task takes its title, dependencies, repositories, and spec from the approved plan and keeps everything else: status, blocker, summary, timestamps, base commits, reports, and handoff. Matching is by folder name. The tool checks the selection against the current plan and task records before approving, and sync checks it again under its lock. It rejects, writing nothing:

- an empty list or a repeated folder;
- a folder that is not a task of the feature, has no readable status, is manual, or is `done` or `cancelled`;
- a folder the plan no longer produces, for example because its heading was retitled. Restore the old title, or add the new work as a new task;
- a repository change while the task has a retained worktree, or when the feature's worktrees could not be listed. Integrate or clean up that worktree first, or keep the task's `Repos:` line unchanged;
- a plan whose resulting unfinished-task graph is invalid.

### Plan sync status

`planSync: { state, hint? }` says whether the stored tasks reflect the current plan content. Sync records its progress in `task-sync.json` in the feature directory, and the status is computed from that record and the current task files each time it is read:

| State | Meaning |
|-------|---------|
| `current` | The last sync reconciled exactly this plan content, and every unfinished plan task still has the title, dependencies, repositories, and spec the plan produces, within a valid dependency graph |
| `changed` | Plan content changed since the last reconciled sync, including edits outside `## Tasks` |
| `incomplete` | The last sync failed, raced a status change, or left a started task unrefreshed, or task records drifted from the synced plan; the hint names up to five affected folders |
| `unknown` | No task sync is recorded (for example, a feature last synced before this record existed), the record is unreadable, or the plan or a task record cannot be compared |

The baseline is the SHA-256 of the raw `plan.md` bytes, the same `contentHash` that `hive_plan_read` reports, so a line-ending rewrite counts as a change. Comments and approval do not. Manual, `done`, and `cancelled` tasks are history and are not compared. Reading the status writes nothing: it creates no record, lock, or directory and repairs nothing; the next sync rewrites a missing or unreadable record. When the status cannot be calculated, a successful mutation still returns its outcome with `planSync.state: 'unknown'`.

The status is advisory. It never approves, syncs, or blocks anything, and it says nothing about whether a worker is running. When it is not `current`, check the affected tasks and shared contracts, then review, approve, and sync as needed before dispatch.

Plans, approval, and dependencies guide work and status visibility. They are not dispatch or status admission gates. Approval and task sync are per-feature. Cross-feature overlap or activity does not block approval; concrete prerequisites block affected execution tasks or lanes unless they leave the plan materially unresolved. Unresolved plan comments still block approval. Hive does not infer cross-feature dependencies. Authored plans keep their structural dependency checks, and sync and manual creation validate the dependencies of unfinished tasks (see [Task dependency graph](#task-dependency-graph)).

## Task Management (3 tools)

| Tool | Purpose |
|------|---------|
| `hive_tasks_sync` | Generate tasks from plan, or refresh pending plan-backed tasks with `refreshPending: true` after a plan amendment; started tasks are refreshed only through `hive_plan_approve` with `refreshTasks` |
| `hive_task_create` | Create an append-only manual task with optional `dependsOn`, `repos`, and structured metadata |
| `hive_task_update` | Update optional task status, summary, blocker, terminal report, or successor handoff; omissions are preserved |

`hive_tasks_sync` takes optional `feature` and `refreshPending` (default `false`) and returns `created`, `removed`, `kept`, and `manual` task folders, `planSync`, and when nonempty `refreshed` (tasks rewritten from the plan), `skipped` (tasks left unchanged because their records changed while sync ran), and `unownedTaskHeadings`. Core sync fails with `TaskSyncError`, which carries a `stage`, `applied: { removed, created, refreshed }` (actions that completed), `interrupted: { action: 'remove' | 'create' | 'refresh', folder } | null`. At `validation` it wrote nothing, and at `checkpoint` it wrote no task file. At `tasks`, `verification` and `publication_unconfirmed` it may have applied the listed task changes, which are not rolled back. `interrupted` names the action that was running when the write threw. It is never listed in `applied`, because a write can fail before or after its rename publishes, so that task's files may be unchanged, partly written, or fully written. A created task is the exception: its folder is staged under a dot-prefixed name and published with its `status.json` and `spec.md` in one rename, so an interrupted create leaves it absent, and a retry creates it, or complete but possibly not yet durable. A leftover `tasks/.<folder>.creating-*` staging directory is never read as a task. A `tasks` failure never attempted the reconciled record, so `task-sync.json` holds `incomplete`. In a `verification` failure every task change was applied and the reconciled write reported an error; sync then read `task-sync.json` back and it held no reconciliation of this plan content, so `planSync` read at that point was not `current`. A `publication_unconfirmed` failure also applied every task change, but the reconciled write reported an error and the read-back failed or found no record, so whether reconciliation was published is unknown and the error text says so. Read `planSync` with `hive_status` before replaying sync after an unconfirmed failure. It describes `task-sync.json` as read then: `current` shows the task data is current now, not what the failed call published, and a later `unknown` or `incomplete` is likewise not a verdict on that call. A later sync records reconciliation without rewriting tasks that already match the plan (see [Plan sync status](#plan-sync-status)). Standalone `hive_tasks_sync` returns this failure as a tool error whose message states whether files changed, lists applied changes, and names an interrupted action; the approve-and-sync call returns `stage`, `applied`, and `interrupted` as fields of its `sync` outcome. `hive_task_create` requires `name`; optional inputs are `order`, `feature`, `description`, `goal`, `acceptanceCriteria`, `references`, `files`, `dependsOn`, `reason`, `source`, `repos`, and `target`, a retained checkout ID the task's worker integrates into (with `repos`, exactly that checkout's repository). It returns the new task folder. It allocates the next order under the feature's `task-sync.json` lock, so concurrent creations and syncs never take the same number, and publishes the folder with its `status.json` and `spec.md` the same way sync creates one. A failure after that publication, flushing the tasks directory or releasing the lock, is a `TaskCreateUncertainError` with `publication: 'published'` whose tool error says the task was created and names its folder: the task exists, so read `hive_status` and do not repeat the create, which would allocate another folder. When the publishing rename itself reports an error, the create is a `TaskCreateUncertainError` with `publication: 'unknown'` and `publishFailure`, because a rename can take effect and still report failure: its tool error says publishing reported a failure and that the task may exist until the feature's tasks are read. Read `hive_status`, and create the task again only if its folder is absent. Every other `hive_task_create` error, including a failure while staging the folder before the rename, created nothing. `hive_task_update` requires `task`; optional inputs are `feature` (string), `status` (`pending` | `in_progress` | `done` | `blocked` | `failed` | `partial` | `cancelled`), `summary`, `report`, and `handoff` (strings), and `blocker` (an object or `null`). A non-null `blocker` requires `status: 'blocked'` or a task already blocked.

Plan-backed tasks get their DAG from `plan.md` `Depends on:` annotations during `hive_tasks_sync`. Modern plans sync numbered task headings only from the `## Tasks` section. Task numbers must be unique; a plan that reuses one is rejected before sync writes anything. A pure final verification checklist belongs in `## Final Verification` unless it writes tracked artifacts.

Sync keeps manual tasks and plan tasks whose current status is not pending (including cancelled ones), with their reports and other files, whether or not the plan still lists them. The test is the stored status, not whether the task has a report or other history. A kept cancelled plan task appears in `kept` and a cancelled manual task stays in `manual`; neither is recreated as pending. A manual task keeps its manual origin and stored dependencies even when a plan heading produces the same folder. A pending plan task missing from the plan is removed with its task folder only when it has no execution history. One with a recorded start, a report, or a handoff, for example a task reset to pending after work began, rejects the sync: restore its heading, or cancel it with `hive_task_update` to keep it as a retained record. With `refreshPending: true`, pending plan tasks still in the plan take their title, dependencies, repositories, and spec from the current plan; started tasks change only through [Selected task refresh](#selected-task-refresh).

A pending status does not prove that no worker holds the task: a primary may have dispatched one without recording `in_progress`. So sync treats a worker placement or binding sidecar under `.hive/.worktrees/` for the task, or a group directory it cannot list, as a worker that may still hold it. The placement is history, not proof that a worker runs, and approve-and-sync also counts a task named in its retained-worktree inventory. Such a pending task is never removed when the plan drops it, and `refreshPending` does not rewrite it when its record differs from the plan; either case rejects the sync, writing nothing. A record that already matches the plan needs no rewrite and does not block the sync. Once its assignment is terminal, refresh it by selecting it in `refreshTasks`, which keeps the placement restrictions under [Selected task refresh](#selected-task-refresh), or integrate or clean up its worktree.

When no `expectedContentHash` is supplied, as in standalone `hive_tasks_sync`, a content-stamped `APPROVED` marker supplies it: if `plan.md` no longer has the approved content, sync rejects before writing anything, so an edit made outside the plan tools is never synced as approved. Approve the current plan to sync it. A marker in neither accepted form is rejected the same way. A legacy marker, or no marker after a plan write or patch revoked approval, leaves the content unchecked; approval stays advisory and is not a sync admission gate. Sync, `hive_task_create`, `hive_task_update`, and the core task-spec and subtask writers also resolve the feature first and refuse an unknown, ambiguous, or unreadable feature before any lock or write. Their paths then lead to the directory resolution chose: a leftover directory that has the feature's name but no `feature.json` is never written in place of the indexed feature.

Sync also protects task identity. It never recreates a plan task folder whose `status.json` is missing; repair the record first. It never creates a new folder for a heading number whose earlier folder holds started or finished work (`in_progress`, `blocked`, `failed`, `partial`, or `done`), which is what retitling that heading would do. Restore the heading title that produces the existing folder, or give the new task its own number. Sync never renames task folders or moves worktrees. Neither sync nor manual task creation creates a `tasks/` record for a folder that a worker placement or binding already claims: such a worker was placed from another record, such as a legacy `execution/` one, and a new record would take over its identity. The call is rejected, writing nothing; integrate or clean up that worktree first.

Syncs of one feature are serialized by the lock on `task-sync.json`. Each refresh or removal rereads the task's status under the same lock as `hive_task_update` and writes only the plan-owned fields, so a concurrent update is kept. A task that is no longer eligible on that reread (a pending task that started, gained history, or gained a worker placement or binding, or a selected task that finished) is skipped, as is a new folder that appeared after sync planned to create it. Manual task creation takes the same `task-sync.json` lock, and so does worktree creation while it claims a task's placement: it takes the `task-sync.json` lock and then the task's status lock, rechecks that the task's status still resolves to the file and record its selection read, and publishes the placement before releasing both, so no sync or creation changes the task's record between that check and the publication.

Task status is the execution record, and only `hive_task_update` writes it. Dispatch and worktree creation do not record that work started, so the primary records `in_progress` immediately before launching a worker for a pending feature task. A failed or unconfirmed launch leaves the worker's state unknown; the primary inspects before resetting the task to `pending`.

### Task dependency graph

A stored `dependsOn` array lists task folders. A status file without the field has no dependencies; folder numbers never imply one. Plan shorthand (a task with no `Depends on:` line depends on the previous task number) is resolved when sync compiles the plan, and the result is stored as an explicit array.

Before writing anything, sync and manual creation check the graph they would leave behind. Each dependency of an unfinished task (`pending`, `in_progress`, `blocked`, `failed`, or `partial`) must name an existing task other than itself, and unfinished tasks must not form a cycle. Dependencies of `done` and `cancelled` tasks are history: they stay in `status.json` and in `hive_status`, but they are not checked. An unfinished task may depend on a done or cancelled task, which must exist; only `done` satisfies the dependency.

A rejected sync or manual creation changes no task files. The error names the unfinished task and its missing target, self-reference, or cycle, then the repair routes that apply:

- A pending plan task with outdated stored dependencies: amend its `Depends on:` line if needed, then run `hive_tasks_sync({ refreshPending: true })`.
- A missing task that a plan heading can recreate under the same folder (`### N. Title` with a free number N and a title that produces the folder name): restore that heading and sync again. Manual creation is append-only and cannot restore an earlier folder.
- An unfinished started plan task (`in_progress`, `blocked`, `failed`, or `partial`) whose plan heading still produces its folder: amend its `Depends on:` line, confirm no assignment for it is running, then approve and sync with `refreshTasks` naming it (see [Selected task refresh](#selected-task-refresh)).
- A manual task, a `done` or `cancelled` task, or a plan task whose heading is gone: no tool edits its stored dependencies, and changing its status does not change them. If the task is obsolete and the operator approves, cancel it with `hive_task_update` and create a replacement with `hive_task_create` when the work is still needed. Cancelling releases its outgoing dependencies. It does not stop a running worker, and it does not rewire tasks that depend on it; those tasks keep the dependency and stay blocked until the operator decides what replaces it. Started work and tasks that depend on the obsolete one need an explicit operator decision; do not bulk-rewrite dependencies.

Sync validates the graph it would produce, not the current one, so a restored heading or refreshed pending task can repair a feature whose stored graph is already invalid, for example after an older sync deleted a plan task that a manual task still referenced. `hive_task_update` does not check dependencies: reopening a done or cancelled task makes its stored dependencies active again, and the next sync or manual creation reports them if they are invalid. Sync is not transactional; the check guarantees only that a rejected call writes nothing, not that a filesystem failure part way through the writes is rolled back. Such a failure reports the changes it applied and leaves `planSync` `incomplete` until a later sync reconciles.

`report` is a nonblank string written to `tasks/{task}/reports/{N}.md` and mirrored to `tasks/{task}/report.md`; it is not a `status.json` field. `handoff` is nonblank, limited to 2048 UTF-8 bytes (rejected rather than truncated), and replaces `tasks/{task}/handoff.md`; other updates leave it intact. The update returns `reportPath` or `handoffPath` when it writes one. An explicit status leaving blocked clears the blocker. All supplied fields are validated before any write; writes then run in order: report history, `report.md`, `handoff.md`, `status.json`. If report-history, latest-report, handoff, or status publication fails, the tool returns `success: false`, `reason: 'task_update_persistence_failed'`, `failedStage` (including `handoff`), the affected paths, and write/publication flags including `handoffPath` and `handoffWritten`. A validation rejection writes nothing. Any other failure, including a lost tool result, may still have written earlier stages, so history can hold the report while `report.md`, `handoff.md`, or status is stale. `failedWritePublished: true` means the failed destination's text matches the attempted content, possibly because it already matched before this call. It does not prove this call wrote the file or that the write is durable; the failed stage's written flag remains `false`. Treat the flags as hints: inspect the files before retrying, and do not resubmit a report that already has a history copy. `report.md` is stale only when the latest report write did not publish; an update carrying only missing status, summary, or handoff fields does not refresh it. There is no journal or repair tool.

A bound implementation Forager calls `hive_task_update({ feature, task, report, handoff })` without `status`, `summary`, or `blocker`, then returns the numbered `reportPath`. When that update fails or its result is unknown, the Forager returns the confirmed history path, the failure stage and flags, the narrative when no history copy is confirmed, and the exact handoff text when the handoff did not publish. The primary records status and summary, repairs missing fields after inspecting the files, appends review-decision, interruption, and closure reports when they apply, and reads report content rather than trusting a path. Report numbers record write order, not author or session identity. Reports stay out of task briefs and the context catalog.

Manual tasks are append-only. `dependsOn` may name existing tasks whether or not they are done; creation applies the graph check above to the new task and to every existing unfinished task, so an older invalid dependency also blocks creation. Review-sourced manual tasks cannot declare explicit dependencies. In `hive_status`, a pending task appears in `runnable` when every stored dependency is `done`; a missing `dependsOn` field counts as `[]`.

## Recovery fields and failure classification

Merge results and ad-hoc cleanup results carry recovery classification fields alongside their operation fields. Feature-task cleanup returns `worktreeRemoved`, `branchDeleted`, `pruned`, and `cleanup` without recovery fields. Create and inspect return workspace information instead. The recovery fields describe where an operation stopped and what the caller may safely do next; an `ALREADY_INTEGRATED` or `NO_TRACKED_CHANGES` no-op also carries them, with `action: 'none'`. The merge tools throw an error, with no mutation and no classified result, for a missing task worktree or ad-hoc run, an unresolved feature, a `repoIds` mismatch, and a source pin that conflicts with the inspected candidate. Failures the merge service classifies come back as `success: false` results. A result with `success: true` can still carry a recovery classification, so read `reasonCode`, `action`, and `cleanup` on every result.

| Field | Meaning |
|------|---------|
| `phase` | Where the operation stopped: `validation`, `preflight`, `integration`, `rollback`, `verification`, or `cleanup`. |
| `reasonCode` | Stable uppercase code naming the condition. |
| `mutation` | Durable target state relative to the operation's starting state: `none`, `applied`, `partial`, `preserved`, or `unknown`. Cleanup itself never changes this value. |
| `retryable` | True only when the exact same tool call may be repeated after satisfying the reported prerequisite and no durable target mutation occurred from this attempt. |
| `action` | The conservative recovery step: `correct_arguments`, `clean_target`, `reconcile_target`, `resolve_conflicts`, `inspect_state`, `retry_same_operation`, `cleanup_only`, `start_fresh_run`, `manual_recovery`, or `none`. |

| `reasonCode` | `phase` | `mutation` | `retryable` | `action` |
|------|------|------|------|------|
| `INVALID_ARGUMENTS` | `validation` | `none` | `false` | `correct_arguments` |
| `INVALID_COMMIT_MESSAGE` | `validation` | `none` | `false` | `correct_arguments` |
| `INVALID_MERGE_MESSAGE` | `validation` | `none` | `false` | `correct_arguments` |
| `MESSAGE_NOT_ALLOWED_FOR_REBASE` | `validation` | `none` | `false` | `correct_arguments` |
| `RUN_NOT_FOUND` | `preflight` | `none` | `false` | `inspect_state` |
| `WORKTREE_NOT_REGISTERED` | `preflight` | `none` | `false` | `inspect_state` |
| `WORKTREE_LINKAGE_INVALID` | `preflight` | `none` | `false` | `start_fresh_run` |
| `WORKSPACE_TOPOLOGY_MISMATCH` | `preflight` | `none` | `false` | `start_fresh_run` |
| `WORKTREE_LOOKUP_FAILED` | `preflight` | `none` | `true` | `inspect_state` |
| `CREATE_UNCONFIRMED` | `preflight` | `none` | `false` | `manual_recovery` |
| `SOURCE_BRANCH_MISSING` | `preflight` | `none` | `false` | `inspect_state` |
| `TARGET_MISMATCH` | `preflight` | `none` | `false` | `inspect_state` |
| `TARGET_DIRTY` | `preflight` | `none` | `true` | `clean_target` |
| `TARGET_RECONCILIATION_REQUIRED` | `preflight` | `none` | `false` | `reconcile_target` |
| `GIT_OPERATION_IN_PROGRESS` | `preflight` | `none` | `false` | `inspect_state` |
| `ALREADY_INTEGRATED` | `integration` | `none` | `false` | `none` |
| `NO_TRACKED_CHANGES` | `integration` | `none` | `false` | `none` |
| `MERGE_CONFLICT_ABORTED` | `integration` | `none` | `true` | `retry_same_operation` |
| `MERGE_CONFLICT_PRESERVED` | `integration` | `preserved` | `false` | `resolve_conflicts` |
| `GIT_OPERATION_FAILED` | `integration` | `none` | `true` | `inspect_state` |
| `ROLLBACK_FAILED` | `rollback` | `unknown` | `false` | `manual_recovery` |
| `POST_INTEGRATION_VERIFICATION_FAILED` | `verification` | `applied` when the operation checkpoint confirms the created commit; otherwise `unknown` | `false` | `inspect_state` |
| `CLEANUP_FAILED` | `cleanup` | `applied` after a completed integration; `none` for cleanup-only runs | `false` | `cleanup_only` |
| `COMPOSITE_PARTIAL` | `integration` | `partial` | `false` | `inspect_state` |
| `OPERATION_RECOVERY_REQUIRED` | `preflight` | `none` when refused before any effect; `unknown` when this operation began mutating | `false` | `manual_recovery` |

- `WORKTREE_LOOKUP_FAILED` on a feature-task merge also reports a workspace whose selected repositories, or the Git common directories behind them, changed while the merge waited for its operation locks. Nothing was changed; inspect the workspace and retry. Ad-hoc merge and the other worktree tools throw the same `repository selection changed while waiting for operation locks` error instead of returning a result.
- `CREATE_UNCONFIRMED` means the worker's workspace record still holds `createUnconfirmed: true`, which inspection reports as `createUnconfirmed: true`: the create that wrote it never confirmed the checkout, so it may be another Git client's. Merge refuses it in every mode, single-root, composite or targeted, feature-task or ad-hoc, before it publishes pending markers or runs a Git mutation, including when the source pin was taken from that inspection. Inspect the checkout, keep or remove it yourself, then clean up and create again; see [Worktree families](#worktree-families-9-tools).
- `OPERATION_RECOVERY_REQUIRED` means an interrupted worktree operation, or a lock file from a host that predates native locking, guards the workspace or one of its repositories. With `mutation: 'none'` this call changed nothing. With `mutation: 'unknown'` this call itself failed after it began mutating, and its own pending markers now guard the resources. Feature-task merge returns the result; ad-hoc tools and the other worktree tools throw the same error. Follow [Interrupted operations and recovery](#interrupted-operations-and-recovery); do not repeat the call until the operation is acknowledged.
- A `finalization` block on a merge, create or cleanup result means the operation returned the rest of that result, but its own bookkeeping failed afterwards: some of its pending markers could not be removed or their removal could not be flushed (`markerError`), or releasing its operation locks failed (`lockReleaseError`; the operating system releases them when the host process exits). The result keeps its `success`, `merged`, `sha`, `reasonCode`, `mutation`, per-repository results and `cleanup` exactly as the operation reported them; nothing was rolled back. When the operation began mutating, `retryable` is `false` on the result and on every per-repository result. `finalization.markers` is `retained` when markers of the operation still exist (also when an `unknown` outcome retained them on purpose): `retainedMarkers` lists exactly those files, later mutations of the resources they guard are refused with `OPERATION_RECOVERY_REQUIRED`, and `finalization.operationId` names the entry to inspect and acknowledge (`action: 'manual_recovery'`). It is `cleared_unflushed` when every marker file was removed but flushing the marker directory failed: nothing guards the resources and there is nothing to acknowledge, but the removal may not survive a host crash (`action: 'inspect_state'`; `operationId` identifies a marker that reappears after one). It is `cleared` or `not_published` when no marker of this call exists (`action: 'inspect_state'`). A create result with `finalization` is the create result without the initial inspection; inspect before relying on it. Every `finalization` block a worktree or retained-checkout mutation returns also carries `note`, the recovery rule above in one paragraph, so the tool descriptions only point at it. A failure thrown before the operation returned a result keeps its own classification. When a feature-task merge reports such a failure as `OPERATION_RECOVERY_REQUIRED` with `mutation: 'unknown'`, its `finalization` block names the operation whose markers it kept.
- `ALREADY_INTEGRATED` means the pinned source is an ancestor of, or equal to, the target under either intent. It is classified after the identity, cleanliness, and active-operation guards and before topology and local-data eligibility, so differing trees or protected ignored data do not turn it into `TARGET_RECONCILIATION_REQUIRED`. The result has `reason: 'already_integrated'`, `merged: false`, `mutation: 'none'`, `filesChanged: []`, `cleanupEligible: true`, no `sha`, and needs no `message`; feature results add `taskUpdateRecommended: true`. A source equal to the target reports `ALREADY_INTEGRATED`. When requested cleanup then fails, `reasonCode` becomes `CLEANUP_FAILED` and `reason` stays `already_integrated`, for each composite repository and for a composite whose every repository was already integrated.
- `NO_TRACKED_CHANGES` applies only to `rewrite-private`: the source is not contained in the target and has no net tracked changes, so nothing is squashed or replayed. The operation is a successful no-op, `merged` stays `false`, and no `sha` is reported. Under `preserve-source` the same source is joined by a normal merge commit with `merged: true` and `filesChanged: []`.
- A squash whose staged change is empty also reports `NO_TRACKED_CHANGES`. This happens when the source's changes already landed beside independent target work, as on a retry after an earlier squash of the same source or after `COMPOSITE_PARTIAL`. Hive clears the squash state Git left (`SQUASH_MSG`) without changing a file and creates no commit; same-call cleanup then relies on the `rewrite-private` attestation.
- A composite no-op aggregate reports `ALREADY_INTEGRATED` only when every repository is contained; any private content no-op makes it `NO_TRACKED_CHANGES`. A graph-only preservation merge counts as an actual merge.
- `TARGET_DIRTY` covers tracked/index dirt and incoming-path collisions. `TARGET_RECONCILIATION_REQUIRED` means the integration topology is unsafe while the target contains local data, including ignored Hive state, dependencies, or build output. Reconcile the pinned target into the source worktree and return fresh pins; do not delete local data to make the retry pass. Hive's preflight scan and immediate or per-pick rechecks protect local data. Git merge flags are not the protection boundary.
- `filesChanged` on a successful integration is the observed difference between the target HEAD immediately before integration and the target HEAD after integration. Composite results flatten entries as `repoId:path`.
- Merge results include `success`, `merged`, `strategy`, `filesChanged`, `conflicts`, `conflictState`, `cleanup`, and the recovery fields above; `sha`, `commitMessage`, `reasonCode`, `repos`, target identities and `provenance` appear when applicable. Both cleanup tools report per-step status for worktree removal, branch deletion, and prune using `not_requested`, `not_attempted`, `already_absent`, `succeeded`, or `failed`, plus a `failures` list in `cleanup`.
- `COMPOSITE_PARTIAL` means at least one repository was integrated and a later repository failed. Earlier repositories remain integrated. There is no rollback of partial composite outcomes.
- When integration succeeds and requested cleanup does not fully complete, including when a cleanup step throws or the pre-cleanup proof fails, the result keeps `success: true`, `merged`, `sha`, and per-repository outcomes, and reports `CLEANUP_FAILED` with `action: 'cleanup_only'`. When a later cleanup action such as metadata removal fails after the worktree, prune, and branch steps ran, those steps keep their observed status and the action is listed in `failures`; a single-root or per-repository exception with no step report leaves every requested step in that outcome `failed`. A composite aggregate may still be partial. Composite `cleanup.failures` names the repository for each per-repository entry, including a skipped proof; a `composite-root` failure has no `repoId`. Repeat only the cleanup step.
- A successful merge that applied a commit carries `provenance`, the outcome of its [integration receipt](#integration-receipts): `{ status: 'recorded', path }` or `{ status: 'failed', error }`. With `failed`, the Git result stands (`success`, `merged`, `sha` and `mutation: 'applied'` are unchanged), requested cleanup is skipped with a `provenance` entry in `cleanup.failures` so the source placement is retained, and the result reports no `reasonCode` with `retryable: false` and `action: 'inspect_state'`, not `CLEANUP_FAILED`. Do not repeat the merge.
- After a `preserve-source` merge commit exists, Hive verifies that the target contains the source. When that check is negative or cannot be read, the result is `POST_INTEGRATION_VERIFICATION_FAILED`: the created commit is not rolled back, no cleanup runs, and `observedTarget` names the created commit.
- A missing, unknown, or incompatible `historyIntent` or `strategy` returns `INVALID_ARGUMENTS` before any lock, Git read, or mutation. When no strategy was resolved, the result omits `strategy`. `strategy: 'rebase'` with `preserveConflicts: true` is refused the same way, because a conflict would leave earlier replayed commits applied under an open cherry-pick.
- A rebase whose replay range contains a merge commit returns `INVALID_ARGUMENTS` from preflight, before topology, local-data checks, or any mutation. Use `squash` under `rewrite-private`, or a normal merge under `preserve-source`.

## Worktree families (9 tools)

Public names are fixed. Git helpers do not change task status, auto-commit source, or assign workers.

The primary calls the matching merge tool with the worker's unchanged verified source pin and inspected target expectation. When retention is not needed, use merge's same-call `cleanup: 'worktree+branch'`; a separate cleanup handles retained state or incomplete cleanup. Batch independent Hive calls in one response/step, while sequencing dependent state changes and integrations sharing a destination. Helper investigates evidence only.

| Tool | Purpose |
|------|---------|
| `hive_worktree_create` | Create or select a feature-task Git workspace |
| `hive_worktree_inspect` | Inspect a feature-task workspace |
| `hive_worktree_merge` | Integrate a feature-task branch |
| `hive_worktree_cleanup` | Remove a feature-task worktree and optionally its branch |
| `hive_adhoc_worktree_create` | Create or select a temporary ad-hoc Git workspace |
| `hive_adhoc_worktree_inspect` | Inspect an ad-hoc workspace |
| `hive_adhoc_worktree_merge` | Integrate an ad-hoc branch |
| `hive_adhoc_worktree_cleanup` | Remove an ad-hoc worktree and optionally its branch |
| `hive_worktree_recover` | List or acknowledge interrupted task and ad-hoc worktree operations |

Canonical workspace names are metadata. Existing slotted or composite workspaces are selectable. Merge wants a clean source, a destination with a clean index and tracked working tree, the pinned SHA, a declared `historyIntent`, and an explicit message when it creates a commit. A commit message needs a nonempty one-line subject, blank line, and nonempty body. Disjoint untracked or ignored destination files may remain when the pinned source contains the pinned target history; rebase also requires a linear replay range. A source already contained in the target returns `ALREADY_INTEGRATED` before this check. For a noncontained source, unsafe topology with local data requires same-worktree reconciliation and fresh pins, even when Git reports a clean worktree because Hive state, dependencies, or build output is ignored. Incoming path collisions always block. Hive preflight and rechecks protect local data without relying on Git merge flags. Locks are operation-local. Dirty, untracked, ignored, and unmerged data is protected; there is no force or rm fallback. Same-call cleanup runs only after a proof across every selected repository; later ambiguous branches stay unless `discard: true` is explicit. `deleteBranch` alone does not discard an unmerged branch: Hive compares the branch with the destination checkout's HEAD commit, attached or detached, and reports branch deletion `already_absent` only when the exact branch ref is missing. A comparison it cannot read is a failed step.

Stable public inputs:

| Tool | Inputs |
|------|--------|
| `hive_worktree_create` | `task`; optional `feature`, `baseRef`, `repoIds`, `candidate` |
| `hive_worktree_inspect` | `task`; optional `feature`, `repoIds`, `candidate` |
| `hive_worktree_merge` | `task`, `historyIntent`; required `expectedTarget` or `expectedTargets`; optional `feature`, `repoIds`, `candidate`, `strategy`, `message`, `preserveConflicts`, `cleanup`, `sourceCommit`, `sourceCommits` |
| `hive_worktree_cleanup` | `task`; optional `feature`, `repoIds`, `candidate`, `deleteBranch`, `discard` |
| `hive_adhoc_worktree_create` | optional `runId`, optional `repoIds`, optional absolute `sourceDirectory`, optional `target` and, with it, `baseRef` |
| `hive_adhoc_worktree_inspect` | `runId`, optional `repoIds`, optional absolute `sourceDirectory` |
| `hive_adhoc_worktree_merge` | `runId`, `historyIntent`; required `expectedTarget` or `expectedTargets`; optional `repoIds`, absolute `sourceDirectory`, `strategy`, `message`, `preserveConflicts`, `cleanup`, `sourceCommit`, `sourceCommits` |
| `hive_adhoc_worktree_cleanup` | `runId`, optional `repoIds`, optional absolute `sourceDirectory`, plus `deleteBranch`, `discard` |

`historyIntent` is required and has no default. `preserve-source` permits only `strategy: 'merge'`, its default; it keeps existing source commits and their messages unchanged and validates only the new merge commit message. `rewrite-private` attests that all source-only history in every selected repository is private and authorized for rewriting; it permits `'squash'`, its default, or `'rebase'`, and rebase also validates every replayed source message. Hive does not prove privacy. For published-history repair, confirm that the known published commit is in the source or target ancestry and verify that it is in the final destination's ancestry before claiming repair.

Merge `cleanup` is `'none' | 'worktree' | 'worktree+branch'` and defaults to `'none'`. Cleanup `deleteBranch` defaults to `false`. `preserveConflicts` defaults to `false`. Do not provide a non-blank `message` with `strategy: 'rebase'`. Failed integrations that began mutating attempt to restore the target unless an actual conflict is explicitly preserved. A restore counts only when the target is back at its initial path, branch and commit with no unmerged path, no Git operation state or lock (including `SQUASH_MSG`, `REVERT_HEAD` and `AUTO_MERGE`) and a tracked tree and index equal to HEAD; untracked and ignored files are left alone. Merge refuses to start with `GIT_OPERATION_IN_PROGRESS` while the target holds such operation state or a lock, before any change, cleanup or pending marker; a lone `AUTO_MERGE`, which successful cherry-picks also leave, does not count. A Git hook that edits a tracked file and then fails a squash or merge commit leaves such an edit, which `reset --merge` keeps: the result is then `ROLLBACK_FAILED` with `mutation: 'unknown'`, the edit stays, and the operation's pending markers stay, so the next mutation of that target waits for [recovery](#interrupted-operations-and-recovery) instead of reading it as untouched. A Git read that fails before the first mutation reports `GIT_OPERATION_FAILED` with `mutation: 'none'` and leaves the destination, including staged content, as it found it. If target identity no longer matches after a commit, `recordOperationCommit` returns `POST_INTEGRATION_VERIFICATION_FAILED` with `mutation: 'unknown'` without rolling back. The same failure after squash staging retains staged operation state for inspection. A preserved conflict leaves an active Git operation in the destination checkout; do not call merge again while that state is active.

Ad-hoc worktrees are temporary workspace metadata only: no run history, evidence ledgers, or reports. The one exception is the [integration receipt](#integration-receipts), which links a resulting commit to its run and records nothing else about the run.

### Integration receipts

Every task or ad-hoc merge that applies a commit records a write-once integration receipt at `.hive/provenance/integrations/<sha>.json` for the merge's resulting commit. It links that commit to the task or ad-hoc run, to the run's Worklog when the host recorded one at ad-hoc create, and to the session and agent that called merge when the host knows them; squash and rebase receipts also link the receipts of the commits they rewrote. No tool argument sets any of this: the host stamps the Worklog at ad-hoc create and the caller at merge. No-op merges write no receipt and carry no `provenance` field. Fields, key, `replaced` links and the write-once rule are in [the data model](DATA-MODEL.md#integration-receipts).

Receipts are advisory and gate nothing. When `provenance.status` is `failed`, the source placement is retained: inspect the run and the destination, then read the receipt at `.hive/provenance/integrations/<sha>.json` for the merge's resulting commit. Clean up with the cleanup tool only when that receipt parses and its `source` and origin match this integration. When it is absent, unreadable or describes a different integration, keep the source placement, tell the operator that the commit's association with its task or run is missing, and clean up only once they accept that. A composite reports each repository's outcome under `repos[repoId].provenance`; the top-level value is `failed` when any repository failed, and one failure keeps every repository's placement and gives every repository's result `action: 'inspect_state'`. For a composite, check the receipt at each `repos[repoId].sha` whose provenance failed, not only the top-level `sha`. A `COMPOSITE_PARTIAL` result also carries the top-level value for the repositories integrated before the stop. Receipts already written stay.

By default, a feature-task worktree lives at `.hive/.worktrees/{feature}/{task}` on `hive/{feature}/{task}`. A `candidate` changes the directory suffix to `{task}--{candidate}` and branch suffix to `{task}-{candidate}`. Composite workspaces put repository worktrees under `repos/{repoId}` and use branches `hive/{repoId}/{feature}/{task}` (with the candidate suffix when supplied). Ad-hoc runs use `.hive/.worktrees/adhoc/{runId}` and branch `hive/adhoc/{runId}`; composite branches are `hive/adhoc/{repoId}/{runId}`. An omitted `runId` is generated; an explicit one must match `[A-Za-z0-9][A-Za-z0-9._-]{0,127}`. The run ID is the branch suffix, so choose a readable one.

Cleanup removes only a placement its caller owns. Before anything changes, and also when the checkout is already gone, a single-root sidecar must name the same owner (task or run), path, repository and branch; ad-hoc cleanup refuses a placement without a sidecar that task records show is a task worker of a feature named `adhoc`, which shares `.hive/.worktrees/adhoc/`, and task get and cleanup refuse one there whose name no task records, which is a run's. Task records are read under the Hive root, also for a run made from a foreign `sourceDirectory`. A sidecarless entry whose owner no record settles stays removable by the call that names it. A composite create refuses while the single-root sidecar of the same name remains, since its manifest would take that worker's path. A single-root create refuses before any effect when the record at its placement names another owner, path, repository or branch, cannot be read, or was never confirmed, also when no worker branch remains; only the worker's own confirmed record is replaced. Two placements can name one single-root branch, such as task candidate `{task}--{candidate}` and a task or run named `{task}-{candidate}`. A placement without a record of its own creates or reattaches that branch (create), integrates it (merge), or deletes it (cleanup with branch deletion) only while no other single-root or targeted record in its group names the same branch, whatever repository path that record holds, and every record there can be read; otherwise the call refuses before any effect, and merge returns a `WORKTREE_LINKAGE_INVALID` preflight failure. Ad-hoc create never reattaches: it refuses a run branch that exists without its checkout. A confirmed checkout switched to another branch is refused with a `preflight` failure and nothing removed; switch it back or keep its work on a branch first.

A worktree-only cleanup keeps the worker's record while its branch remains, so the branch keeps a known owner: the single-root sidecar, or a composite's `workspace.json` in a root that then holds nothing else. Such a root is metadata, not a checkout: worker inspect and get return `null`, list and status omit it, merge refuses it, and create refuses it and points to cleanup with branch deletion. A root counts as metadata only when its manifest's create was confirmed, every checkout it names is gone and no longer registered with Git, and it holds nothing but an empty `repos/` and `workspace.json`; any other composite root is read as a workspace, so its errors stay visible. A later cleanup finds the branches through that record and removes the record with the last branch. Cleanup removes a record only after the worktree is gone and a final read finds the exact worker branch absent; that read covers the moment it ran, not what another Git client does afterwards. When a worker branch cannot be read, or exists after the cleanup deleted it or found it gone, cleanup keeps the record and reports itself incomplete, with a `metadata-removal` failure for a single-root or targeted worker and a `composite-root` failure for a composite. A worktree-only cleanup that keeps a readable branch is complete.

A `null` from worker inspect or get means there is no complete, usable live worker. It does not show that every checkout, branch or record is gone: an ad-hoc composite with one repository checkout missing or unregistered also returns `null` while its other checkouts remain. A `null` never permits recreating or deleting anything, and create refuses a root that holds content. Read `hive_checkouts_list` for what remains. It lists a worker whose checkout is gone with `retained.branchCommit`, and adds an `error` beside that branch tip when the record is not only what a worktree-only cleanup keeps: a partial composite removal, a create that never confirmed its checkout, or a checkout Git still registers. It reports, without reading through them, a symlinked worktree root, group or placement, a sidecar declaring no supported mode, a kept sidecar whose placement is not a directory, and a record that does not name the owner, path and branches its placement implies (and, for a task's single-root sidecar, the project repository); such a record gets an error and no Git read. A run made from a foreign `sourceDirectory` whose repository the project does not configure is listed with `repoId: null` and an error, and its branch is not read. The listing is a read-only snapshot taken without locks, so entries can change while it runs. Global stale-workspace cleanup keeps a metadata-only root while one of its worker branches remains or cannot be read, and removes it once every branch is gone.

When a single-root feature-task branch exists without its worktree, as after a cleanup that kept the branch, create reattaches that branch; it never recreates or deletes it. Cleanup keeps the workspace metadata (`{task}.json` beside the placement) while the branch remains, so the reattached workspace keeps its recorded `baseCommit` and its diff still shows the branch's own work. Without that record, the baseline is the branch's fork point with the creation base. A record that describes another workspace, or a baseline the branch does not contain, refuses the create before any effect until it is repaired or removed. A failed create rolls back only what it made: it creates a new task branch in one step that fails when the branch already exists, then attaches the worktree, so a branch it did not create, including one another Git client made after the preflight, stays. Owning the branch does not make the placement path the create's: when its own `worktree add` failed and something is at the path, such as another client's checkout, the create keeps that placement, its registration, the branch and its pending markers. It removes a worktree it did attach only while that worktree is still registered on its branch at the commit it attached and holds no changed, untracked or ignored files; otherwise the worktree stays and is reported.

Every create, feature-task or ad-hoc, single-root, composite or targeted, writes its workspace record (the `{task}.json` or `{runId}.json` sidecar, or `workspace.json`) with `createUnconfirmed: true` before it creates a branch or worktree, and removes the field only after its own `worktree add` succeeded and the registration, branch and HEAD checked out. A record that keeps the field outlives the operation's markers: acknowledging the operation through `hive_worktree_recover` does not show that the checkout at the placement is Hive's, because another Git client may have attached one, even on the worker's own branch. For such a record, inspection reports `createUnconfirmed: true`; merge refuses the worker with `CREATE_UNCONFIRMED`; cleanup removes a checkout only when it is registered on the worker branch and holds no changed, untracked or ignored files, and otherwise keeps it with its registration and reports it; create refuses to return it as an existing worker. Cleanup keeps such a record while a worker branch remains, so a checkout attached to that branch later still reads as unconfirmed; a composite workspace keeps its root and `workspace.json` with it, and that cleanup reports the kept root as a `composite-root` failure, never as a complete removal. A create that finds such a record beside a retained worker branch whose checkout is gone refuses to reattach the branch, because it may carry another Git client's commits; the record goes, and create starts over, only once the branch is deleted through cleanup with branch deletion or by hand. Once the operator has removed or emptied a kept checkout, cleanup finishes. A create that rolls back completely puts back the record it found, such as a retained branch's baseline. When the confirming write itself fails, the add was validated but the record may already read as confirmed, because the atomic rename can publish it before the directory flush fails; the create writes `createUnconfirmed: true` back before it reports what its rollback kept. If that write fails too, its error names the record as unresolved and its markers stay. Recovery does not read workspace records and no Hive tool repairs one, so an agent does not acknowledge the operation: it keeps the record and the kept checkout as they are and reports both to the operator, whose separately authorized repair (setting `createUnconfirmed: true` in the record, or removing the checkout) comes before acknowledgement. Records without the field are confirmed, and cleanup of a confirmed worker still deletes ignored dependency and build output. Any value other than `true` makes the record unreadable.

A composite create writes `workspace.json`, with each repository's resolved base commit, before it adds the first repository worktree. When the create fails and cannot roll back every repository, it reports the original failure together with what remains, keeps the manifest unconfirmed with its pending markers, and the matching cleanup tool removes what is gone or empty after the operation is acknowledged. An empty workspace directory, which an interrupted create or composite-root removal can leave, does not block a later create.

A targeted worker integrates into a [retained checkout](#retained-checkouts-7-tools) instead of the project root or its composite repositories. It exists only when a caller names the target: a task's stored `target` (from `hive_task_create` or a plan task's `**Hive target**: <repoId>/<slug>` line) or `target` on `hive_adhoc_worktree_create`. Hive never picks one from the current checkout. The worker is one worktree in the target's repository, at the usual placement path, on branch `hive-targeted/task/{feature}/{task}` or `hive-targeted/adhoc/{runId}`, with mode `targeted` or `adhoc-targeted`. Its sidecar freezes the target's ID, path and branch at creation. Inspection adds `repoId` and `targetBinding: { id, path, ref, status, detail? }`, and its top-level `target` is the retained checkout, not the project root. `status` is `ok`, `ref_changed` (the checkout left the bound branch), `record_changed` (the record is gone or names another path or branch) or `unavailable` (the checkout cannot be read). Merge returns `TARGET_MISMATCH` for `ref_changed` or `record_changed` and `GIT_OPERATION_FAILED` for `unavailable`, with no mutation in either case. A targeted worker always takes the scalar `sourceCommit` and `expectedTarget`. An ad-hoc `baseRef`, accepted only with `target`, starts the run from a commit other than the target's HEAD, for example the tip of another retained checkout whose work it builds on; integration still goes only to the bound target. `target` cannot be combined with a foreign `sourceDirectory`. Untargeted workers, their paths, branches and pins are unchanged.

On creation, `repoIds` selects the repositories owned by the lane. Later feature-task lifecycle calls validate `repoIds` against the task's persisted repository selection; later ad-hoc lifecycle calls pass the same `runId` and the same `sourceDirectory` or `repoIds` used at creation. `sourceDirectory` selects a foreign checkout and cannot be combined with `repoIds`; it also sets the service root, so inspect, merge, and cleanup of a placement created for a foreign checkout must pass that same absolute `sourceDirectory`. For create, an absolute path resolving to the active project root is treated as omitted, so it may be supplied with project/manifest `repoIds`.

Manifest-backed ad-hoc creation requires a nonempty `repoIds` selection. Omitting it reports a topology error before Git runs; inspect the project repository manifest and select the repositories owned by the run.

When a manifest-backed project's root is not a declared Git repository, lifecycle tools require the selected workspace's `workspace.json`. A wrong task folder, candidate, or run ID, a repeat cleanup after that metadata was removed, or an existing directory without metadata reports `Composite workspace manifest not found` with the expected path before running Git against the project root. Check the exact selector and retained placement; `repoIds` and source pins cannot replace missing workspace metadata. Status reports invalid entries in `worktreeErrors: [{ path, reason }]` and keeps healthy worktrees and task summaries readable. Hive preserves those directories for inspection. Existing single-root placements remain readable when the project root is still a declared repository, including a symlink alias of that root.

For an orphaned composite workspace whose metadata cannot be recovered, an operator or authorized primary may perform the manual recovery below. Helper may inspect and return evidence but cannot execute removal, pruning, or branch deletion, and a failed Hive tool never authorizes Helper to reproduce it with raw Git.

To remove confirmed orphan registrations:

1. Use the reported workspace path and `.hive/repositories.json` to identify the owning repository roots. A feature task's `status.json` `repoIds` and retained `repos/<repoId>` directories help locate the selection. Confirm every exact worktree path and branch with `git -C "<repository-root>" worktree list --porcelain`; do not run Git from a non-Git project or composite root. Preserve source commits and local files before removal.
2. For each confirmed repository, inspect `git -C "<workspace-path>/repos/<repoId>" status --short --ignored`, then run `git -C "<repository-root>" worktree remove "<workspace-path>/repos/<repoId>"` only after its work is integrated or its contents have been deliberately retained elsewhere. If the worktree directory is already absent, review the stale registration and run `git -C "<repository-root>" worktree prune`. Also prune after successful removal.
3. After confirming the branch is integrated and is not checked out elsewhere, run `git -C "<repository-root>" branch -d "<confirmed-branch>"`. Use the branch from the registration, with the feature/ad-hoc and candidate naming described above. If Git refuses removal or branch deletion, retain the state and resolve the cause before retrying.
4. Once every repository registration is handled, remove only empty `repos/<repoId>`, `repos`, and workspace directories with `rmdir`. Retained files must be inspected and preserved before those directories can be removed. Refresh `hive_status` to confirm the orphan diagnostic is gone.

Use `sourceCommit` for a legacy single-root workspace and for a targeted worker, whose inspection has no `repos` even when its task lists one repository. For an inspected untargeted composite workspace, use `sourceCommits` as a complete map keyed by persisted repository ID. A singleton composite also accepts a matching scalar `sourceCommit` convenience; multiple repositories still require the complete map. At the tool boundary, the runtime fills an omitted source pin from its own source inspection at merge time. That selects the source as observed in that call. It does not show that the source was ever verified, and it is the only thing the omission means: a worker-returned pin identifies the candidate the worker checked, and omitting the pin cannot recover that identity if the source has since moved. A supplied composite map must match every inspected repository; it rejects a map for a legacy single-root workspace, a scalar for a multi-repository composite, both pin forms together, and any supplied pin that differs from the inspected candidate, so a stale explicit pin fails before any mutation while an omitted one merges the newer source. In a worker handoff, pass the worker's returned topology-aware pin unchanged to merge.

Both create tools return the initial inspection directly, in the same shape as their inspect tool: placement, source `commit`, `baseCommit` or `baseCommits` when recorded, `clean` (including untracked and ignored dirt), and destination state. A reused worktree is inspected again, so its result reflects current state. Composite results include per-repository source commits and cleanliness under `repos[repoId]`, plus aggregate `clean`. There is no additional inspection wrapper or duplicate placement projection.

A legacy inspection has top-level `target` and `comparison`; composite results put them only under `repos[repoId]`. `target` is `{ path, ref, commit }`, where `path` is the canonical absolute destination root, `ref` is the full `refs/heads/...` name or `null` when detached, and `commit` is the full OID. If destination identity cannot be read, inspection retains source details and returns `target: null` with `comparison.status: 'error'`. Comparison is one of `{ status: 'ok', targetIsAncestorOfSource }`, `{ status: 'no-common-ancestor' }`, or `{ status: 'error', error }`. A shallow repository may therefore report locally no common ancestry; inspection never fetches and ancestry does not establish semantic completeness. Record the initial target identity from create before dispatch. Later inspect checkpoints after writing handoffs, before review/remediation, after sibling integration or destination movement, and before integration remain required.

Every merge must include exactly one target expectation: the exact inspect value as `expectedTarget` for legacy mode, or `expectedTargets` as a complete map for composite mode. In a composite, the map's keys must equal the candidate's repository IDs, and each value is that repository's `repos[repoId].target` from inspect. A singleton composite accepts a scalar expectation and normalizes it without changing identity values. Missing, both, malformed, extra, or topology-incompatible expectation forms fail with `INVALID_ARGUMENTS`. The two target fields stay optional in the argument shape because the choice depends on the workspace; the merge service validates the rule. Runtime forwarding never fills or refreshes target expectations. `TARGET_MISMATCH` includes expected and observed identities, performs no mutation, is not retryable, and requires `inspect_state`. All composite targets are checked before the first repository mutation and each target is checked again at its integration boundary. Earlier composite integrations remain when a later boundary fails.

The identity guard coordinates Hive operations under the existing repository locks. It does not exclude arbitrary Git writers or another lock namespace; callers still need exclusive destination ownership. Squash integration rechecks identity after staging and before commit. If it moved, Hive leaves the source and staged operation state for inspection and reports post-integration verification with unknown mutation rather than committing or destructively resetting external changes. Before any destructive same-call cleanup, Hive rereads the full target path/ref/commit and the source pin, including for no-op cleanup, and checks the proof the completed work requires: source containment in the target for `preserve-source` merges and `ALREADY_INTEGRATED` no-ops, or verified completion plus the `rewrite-private` attestation for squash, rebase, and private content no-ops. A composite proves every repository before removing anything. A failed proof retains every source placement and reports a `cleanup.failures` entry (`identity-recheck` or `ancestry-proof`).

### Interrupted operations and recovery

Worktree operations hold operating-system locks on their workspace and on the Git common directory of each repository they select. The operating system releases a lock when the holding process exits, so a crashed or rebooted host never leaves an operation lock that blocks later work. A read (inspect) holds the same locks and records nothing.

A lock that disappears with its host does not show that the host's work stopped or finished: a Git command the host started can keep running, and a mutation can stop half-done. So a create, merge, remove or cleanup writes one pending marker per workspace and repository it guards (`.hive/.locks/operations/`) immediately before its first workspace or Git mutation. Preflight, reuse of an existing workspace, and refusals before any effect write none. The operation removes its markers when every Git command it ran has finished with a known outcome. It keeps them when it stops part-way, reports `mutation: 'unknown'` (including a failed rollback), or throws after it began mutating. When it finished but cannot remove its markers, it keeps them and reports its result with a `finalization` block.

While a marker remains, or a `.hive/.operation-locks/<name>.lock` file from a host that predates native locking is present, every later mutation of that workspace or repository is refused before any effect with `OPERATION_RECOVERY_REQUIRED`. Inspection keeps working and adds `pendingOperations` to its result, one entry per interrupted operation or legacy lock file:

| Field | Meaning |
|------|---------|
| `operationId` | The marker's ID, or `legacy:<name>` / `unreadable:<name>` for a legacy lock file or a marker that cannot be parsed |
| `state` | `interrupted`, `legacy_lock`, or `unreadable_marker` |
| `marker` | For `interrupted`: `kind`, `subject` (task or ad-hoc run), the exact `workspacePath` and repositories, `startedAt`, a diagnostic `pid`, and, when the operation knew them, each repository's `sourceCommit` and `expectedTarget` checkpoint and the merge `strategy` |
| `record` | For a legacy or unreadable record: its path and leading bytes |
| `observed` | Current destination identity, source branch and commit, and Git operation or lock state (`MERGE_HEAD`, `SQUASH_MSG`, rebase or cherry-pick state, `index.lock`, `HEAD.lock`, `packed-refs.lock`, the source branch's ref lock) of every guarded resource |
| `markerDigest`, `observedStateDigest` | Digests a recovery call must present unchanged |
| `recovery` | `{ available: true }`, or `{ available: false, reason }` for a record whose resource this project cannot identify, or a marker that names a workspace outside the project's worktree placements, a repository outside its trusted repositories, a source checkout that is not a checkout of the marker's workspace (for a project-wide cleanup, which names no workspace, of any worktree placement), a guarded checkout reached through a symlink or whose `.git` linkage does not select its trusted repository, or a malformed branch name; such a record is preserved |

Marker files are untrusted data. Before Hive reads anything a marker names or runs Git there, it checks the declared paths against the project and checks every checkout it would observe on disk: no symlinked path component, and a `.git` pointer, `commondir` and backlink that register it as a worktree of the expected trusted repository. An entry that fails either check has an empty `observed` (`workspace: null`, no repositories): nothing it names was read, and an empty observation there does not describe the named paths.

The checkpoints describe what the interrupted operation intended. They are evidence for deciding the next step, never an instruction to replay it. Git can run without holding any lock Hive can see (a commit hook, for example), so an empty `activeGitState` does not show that the operation stopped.

`hive_worktree_recover` without arguments lists every such entry in the project, including those whose workspace is gone. To acknowledge one entry, a primary first confirms that no process of the operation is still running, including a Git child that outlived its host, and that Git has no unresolved operation in the guarded checkouts. Then it calls the tool with the entry's `operationId`, `markerDigest` and `observedStateDigest` from its latest listing or inspection, and `mutatorsStopped: true`. The tool takes the same operation locks and refuses, removing nothing, with `success: false` and a `reason`:

| `reason` | Meaning |
|------|---------|
| `attestation_required` | `mutatorsStopped` was not `true` |
| `operation_not_found` | No entry has that `operationId` |
| `recovery_unavailable` | The record's resource cannot be identified in this project; for a legacy lock or unreadable marker of a workspace that no longer exists, pass its `workspacePath` |
| `resource_untrusted` | A recorded workspace, repository or source checkout is not part of this project (pass the run's absolute `sourceDirectory` for an ad-hoc run on a foreign checkout), or a repository now resolves to another Git common directory, including after it changed while recovery waited for the operation locks |
| `marker_changed` | The entry's records changed since the listing |
| `git_operation_active` | Git operation or lock state remains in a guarded checkout; resolve or abort it with Git first |
| `observed_state_changed` | Source or destination state changed since the listing; list or inspect again |

A legacy lock file or unreadable marker names its workspace only by a hash, so Hive identifies it from the workspace directories that exist. For a workspace that no longer exists, pass its canonical absolute placement as `workspacePath` (`.hive/.worktrees/<group>/<name>` or a retained checkout's `.hive/checkouts/<repoId>/<slug>`, as inspect or create reported it) to both the listing and the acknowledgement. Hive accepts only a placement of this project and derives the hash itself, so the path maps only that workspace's own record; a repository record that no trusted repository matches stays unavailable. Acknowledging such an entry also requires, under the workspace lock, that the workspace is still absent, through no symlinked path component (`observed_state_changed` when it exists, `resource_untrusted` when that cannot be shown), and that no trusted repository still registers a checkout inside it (`git_operation_active`; review the registration and run `git worktree prune` first). A trusted repository Git cannot list refuses with `resource_untrusted`; only a manifest project's root that holds no `.git` is skipped.

A successful call removes only that entry's record files and returns `{ success: true, operationId, state, cleared, replayed: false }`. It never runs, retries or rolls back the interrupted operation and never touches another operation's records. Inspect again before deciding whether the merge, cleanup or create still needs to run.

## Retained checkouts (7 tools)

A retained checkout is a named, long-lived branch checkout that targeted workers integrate into, for example a release line beside `main`. Its ID is `<repoId>/<slug>`, both parts in the repository ID grammar; a project without `.hive/repositories.json` has the one repository `root`. A **managed** checkout is a linked worktree Hive creates at `.hive/checkouts/<repoId>/<slug>/`. A **registered** checkout is a checkout the project already configures (the root or a manifest repository), recorded at its current branch; Hive never creates, moves or removes it or its branch. Each has a record beside it, `.hive/checkouts/<repoId>/<slug>.json`; `.hive/repositories.json` does not change. A session opened inside a managed checkout resolves to the project that holds it, with no feature or task.

| Tool | Inputs | Purpose |
|------|--------|---------|
| `hive_checkouts_list` | none | Every repository with `root`, live `head` or `headError`, its checkouts (`present`, live `head`, `onIntendedRef`, readiness with `headMoved`) and its task and ad-hoc workers (a worker shows `target` only when it has one, and `retained: { branchCommit }` when its checkout is gone while its record and branch remain); per-entry problems in `error` or `errors`. Reads records and read-only Git; never fetches or writes |
| `hive_checkout_inspect` | `id`; optional `local`, `cleanup` | One checkout as `checkout`; `local: true` adds modified, untracked and ignored paths; `cleanup: true` adds the cleanup proposal |
| `hive_checkout_brief` | `id`; optional `against` | What the checkout holds relative to a destination checkout and which Hive integrations produced it; see [Checkout brief](#checkout-brief). Writes no Hive state and runs no fetch command; an older Git can still lazy-fetch objects in a partial clone |
| `hive_checkout_create` | `id`, `branch`; optional `baseRef`, `purpose` | Create a managed checkout on a new branch from `baseRef`, or on an existing branch checked out nowhere else |
| `hive_checkout_register` | `id`; optional `purpose` | Record a configured checkout at the branch it has checked out now |
| `hive_checkout_readiness` | `id`, `expectedTarget` (identity, or `null` with `expectedRecord`), `readiness` (`{ state: 'ready' \| 'not_ready', nextTarget?, waitingFor? }` or `null`); optional `expectedRecord` | Declare, replace or clear readiness at the checkout's current commit; clear it on a missing checkout |
| `hive_checkout_cleanup` | `id`, `expectedTarget` (identity or `null`); optional `removeIgnored`, `deleteBranch` (`{ containedIn }` or `{ discard: true, commit }`) | Remove an unreferenced checkout |

Mutations return `{ success: true, checkout }` (cleanup: `{ success: true, id, ownership, worktreeRemoved, branchDeleted, recordRemoved }`). A refusal the checkout service classifies returns `{ success: false, reason, error }` and changes nothing; `reason` is one of `invalid_id`, `not_found`, `record_invalid`, `repository_unknown`, `binding_mismatch`, `invalid_destination` (a brief's `against` is the checkout itself or another repository's), `referenced`, `references_unknown`, `local_data`, `not_contained` and `user_owned`. `OPERATION_RECOVERY_REQUIRED` comes back the same way with `mutation` and `operationIds`: an interrupted worktree operation guards the repository, so use `hive_worktree_recover` instead of repeating the call. Other invalid requests, such as a malformed branch, are tool errors. A result can carry the `finalization` block described above. Create and register are idempotent for an identical request and never overwrite a different checkout, path or branch.

### Checkout brief

`hive_checkout_brief({ id, against? })` is the read to take before integrating one retained checkout into another. The destination is `against` when given, else the source's declared readiness `nextTarget`; Hive never picks `main` or the project root. With neither, or when a destination HEAD cannot be read, `comparison` is `{ status: 'unresolved', reason }`, the source overview still returns, and `contributions`, `alreadyInDestination` and `unattributedCommits` are `null`. An unknown or malformed `id` or `against`, or an `against` that is the source or belongs to another repository, returns `{ success: false, reason, error }`; a declared `nextTarget` that cannot be used only leaves the comparison unresolved.

A successful result is `{ success: true, repoId, source, destination, comparison, contributions, alreadyInDestination, unattributedCommits, gaps, notice }`:

| Field | Content |
|---|---|
| `source`, `destination` | `id`, `purpose`, `present`, live `head` (`{ path, ref, commit }` or `null`) and `onIntendedRef`. `source.readiness` is the stored declaration, including `declaredBy` when present, plus `headMoved` |
| `comparison` | `destinationFrom` (`against` or `nextTarget`), `mergeBase`, `ahead` and `behind` counts, `commits` in `destination..source` (`sha`, `subject`) and `changedFiles` of the three-dot diff (`null` without a merge base) |
| `contributions` | One entry per integration receipt the source brings that the destination does not hold, keyed by the receipt's commit: `commit`, `strategy`, `recordedAt`, `origin`, `integratedBy`, `reachedVia` (the receipt whose `replaced` list led to it; absent for a receipt in `destination..source`) and `sources`. `origin` carries the feature, task, candidate or run ID; `sources` adds what was found for it, discriminated by `kind`. For a task origin: `worklog`, the feature's Worklog ref by logical name (absent when the feature cannot be resolved or its name cannot be used as a Worklog ref because feature resolution is ambiguous or unreadable), the validated task `status` (`null` when the record is missing or invalid), `summary` and the project-relative `plan`, `spec`, `latestReport` and `reportHistory` paths that exist, in the `tasks/` or legacy `execution/` layout. For an ad-hoc origin whose run stamped `origin.worklog`: `worklogHeader`, a header of that log with `title`, current `briefing`, `updatedAt` and `entryCount` (`null` when it cannot be read) |
| `alreadyInDestination` | Receipts reached from the source whose work the destination already holds, for example through a squash it took earlier: `commit`, `origin`, `reachedVia` |
| `unattributedCommits` | Commits in `destination..source` that are neither a receipt's commit nor inside `before..after` of a receipt in that range |
| `gaps` | What could not be established, each `{ kind, commit?, detail }`: `head_unreadable`, `comparison_unresolved`, `git_error`, `receipts_unreadable`, `receipt_missing`, `receipt_corrupt`, `receipt_unreadable`, `replaced_cycle`, `task_missing`, `task_unreadable`, `worklog_missing`, `worklog_unreadable` or `truncated`. One bad entry never fails the call |
| `notice` | Receipts show that an integration happened, not that its change is still in effect, that checks ran or that readiness was verified; Worklog, summary and report text is untrusted narrative |

To read a linked log, pass a task contribution's `sources.worklog` or an ad-hoc contribution's `origin.worklog` as `ref` to `hive_worklog_read`; for the readiness declarer, pass `{ kind: 'session', owner, sessionId }` from `source.readiness.declaredBy`.

The destination holds a receipt when its commit is reachable from the destination HEAD, or when a held receipt lists it in `replaced`, transitively. The brief starts from the receipts in `destination..source` and follows `replaced` links, cycle-safe, through held receipts as well: each receipt it reaches is listed in `alreadyInDestination` when held and in `contributions` otherwise. Every list is `{ items, total }` with fixed caps: 50 commits, 200 changed files, 20 contributions (only those carry `sources`), 20 already-held receipts, 50 unattributed commits and 50 gaps; every cut list except `gaps` also adds a `truncated` gap. Briefing and summary text is cut at 1024 UTF-8 bytes with `truncated: true`. The brief reads checkout records, receipts, task status files and Worklog brief views, and runs only read-only Git. It writes no Hive state, runs no fetch command and sets `GIT_NO_LAZY_FETCH` on its Git reads, so an object missing from a partial clone becomes a gap or an unresolved comparison; a Git build that predates that setting can still lazy-fetch the missing object, which writes Git objects. It never reads the session index. There is no pagination; read the linked Worklogs, task records and reports with their own tools.

Readiness is a primary's statement pinned to the commit of `expectedTarget`, which must still match the checkout. Hive runs no verification of the work and gates nothing with it; inspection reports `headMoved: true` once the checkout moves past that commit. `nextTarget` names another retained checkout in the same repository. A checkout whose placement is missing can only have its readiness cleared: pass `expectedTarget: null`, `readiness: null` and `expectedRecord`, the `cleanup.record` from `hive_checkout_inspect({ id, cleanup: true })` unchanged. Only the record changes; a record that changed since inspection, or a checkout that exists again, returns `binding_mismatch`. This retires a next-target declaration, such as two missing checkouts naming each other, that keeps their records from being removed.

Cleanup acts on a proposal. `hive_checkout_inspect({ id, cleanup: true })` returns `cleanup: { record, present, identity, onIntendedRef, local, references, unreadableReferences, pendingOperations, blockers }`. `references` lists unfinished tasks whose `target` names the checkout, targeted workers bound to it (including one whose worktree is gone while its branch remains) and other checkouts' `nextTarget` declarations, each with the file that holds it (`statusPath`, `sidecarPath` or `recordPath`); `unreadableReferences` lists sources that could hold a reference but could not be read. Cleanup refuses while either is nonempty. The proposal is a second read, so `cleanup.identity` can differ from `checkout.head` in the same result; pass `cleanup.identity` unchanged as `expectedTarget` (or `null` when the proposal found a managed checkout missing). A registered checkout only loses its record. A managed checkout must still be exactly that identity, on its intended branch, with no Git operation in progress and no modified or untracked files; ignored content is removed only with `removeIgnored: true`. Its worktree and record are removed and its branch kept, unless `deleteBranch` is `{ containedIn: '<id>' }`, another retained checkout of the same repository on its intended branch whose branch contains this one, or `{ discard: true, commit }`, which deletes the branch only while it is still at that commit. The argument schema declares `discard` as a boolean, because some providers reject a boolean literal in a tool schema. In the discard form, `discard` must be exactly `true`; any other value is refused, as is a `deleteBranch` of neither form, before anything is locked or removed. Input that matches the containment form is read as containment, with extra keys such as `discard` stripped, and deletes the branch only when containment is proven. To keep the branch, omit `deleteBranch`.

The reference scan is not transactional. Retained checkout and worktree operations on the repository wait for its operation lock, but task writes take their own locks and processes outside Hive take none, so a task record that starts naming the checkout while cleanup scans can go unseen. When the checkout must stay unreferenced, stop task updates and other writers that could name it until cleanup returns.

## Live Subagent Children (2 tools)

Both tools are primary-only. They act on the calling session's direct subagent children in the plugin's location, read them live when called, and write no `.hive` file: Hive keeps no record of background launches. Every answer is a sample at the time of the call. The host schedules, runs, interrupts and notifies background children and reports each child's result to its parent; these tools only read and interrupt.

| Tool | Purpose |
|------|---------|
| `hive_background_status` | List the calling session's direct children that still have work running, or read whether one child's whole session tree has settled |
| `hive_background_cancel` | Interrupt one direct child's active execution, with resume disabled |

On OpenCode v1 both tools are registered so the tool set matches, and each always returns `{ success: false, reason: 'unsupported_on_host', error }`: a native `task()` call blocks until its child returns, so there is no live background child to read or stop.

`hive_background_status` takes optional `sessionID`, `feature`, `task`, `adHocRunId`, and `includeSettled` (default `false`). The feature, task and run filters match the binding Hive wrote when it dispatched the child; a child without a binding has an empty `scope`. A child that the caller did not dispatch through Hive has no binding.

- Without `sessionID`, it lists the direct children from the in-process session list, then reads the server's jobs and active executions once. The result is `{ success: true, coverage: 'jobs_and_executions', working, children?, note, warnings? }`. Each `working` entry has `sessionID`, `agent` and `outcome` when the host reports them, `scope` (`feature`, `task`, `adHocRunId`), `jobs` (`kind`, `status`, and `owner`: `parent`, `child` or `descendant`) and `activeExecution`. `children` lists the remaining matching children only with `includeSettled: true`. This list does not read queued inbox input; `note` says so.
- When the live reads fail, the result is still `success: true` with `observation: { available: false, readAccess, message }`, every matching child under `children`, and a warning that none of them may be treated as settled. `readAccess` is a verified-reader code (`not_configured`, `unauthorized`, `unreachable`, `wrong_location`, `wrong_instance`, `caller_unavailable`, `caller_displaced`, `target_unavailable`, `inconsistent_lookup`, `malformed_response`) or `read_failed` for any other failure.
- With `sessionID`, it reads one child. A session that is not a direct child of the caller in this location returns `{ success: false, reason: 'not_a_child', error }`. A child whose binding does not match the given filters returns `{ success: false, reason: 'scope_mismatch', error, warning? }` without reading its settlement. Otherwise the result is `{ success: true, ...view, settlement, settled?, warning? }`: the child's view plus `settlement: { available: true }` and `settled: true`, or `settled: false` with `signal` (`job`, `inbox` or `active`) and `detail`. Settled means no job the host lists for the child or its descendants, no queued inbox input, and no active execution in any session of the child's tree. When the read fails, `settlement` is `{ available: false, readAccess, message }` and no `settled` field is present.
- When Hive cannot read its own child bindings, the result carries a warning (`warning` for one child, `warnings` for the list) and the scope fields are missing. The live reads still run, except that a `sessionID` call with filters stops at `scope_mismatch`, because the missing scope cannot match them.

`hive_background_cancel` takes `sessionID` and an optional `reason`. A session that is not a direct child of the caller in this location returns `not_a_child`. Otherwise Hive asks the host to interrupt the child with resume disabled and returns `{ success: true, sessionID, interrupted, message }`. `interrupted: true` means the host interrupted an active execution. `interrupted: false` means the child had no active execution; the result then also reads the child's settlement, with the same fields as a `sessionID` status read, because an idle child may still have background work.

Interruption is not rollback and does not prove that the worker stopped. Interrupting a session stops only its active model execution: `shell` commands and descendant jobs it already moved to the background keep running and can wake it again when they finish. An `error` or `cancelled` report from the host ends one execution, not those commands and jobs. Before starting an overlapping writer, read the child with `hive_background_status({ sessionID })` and confirm its tree has settled.

Call `hive_background_status` when a child's liveness is uncertain, for example after an interrupted run, a timeout or a restart; a normal launch needs no status call, because the host posts the child's final report. Call `hive_background_cancel` only to stop a wrong, stale, or unneeded child. On v2 a `subagent()` child keeps running after its parent's turn is interrupted or ends.

### V2 subagent dispatch and continuation

V2 dispatch binds the captured parent route and constraints at the awaited native progress update, before the host admits the child's prompt. At that barrier it first writes the route, the session and feature constraints with their revisions, and the bound `Task:` or `Ad-hoc run:` line as the child's `hive.session` session instruction entry; a child whose entry cannot be written is refused and never prompted, and its Hive binding is left unchanged. When the binding write then fails, only a continued child already bound to the same route and the same task or run still runs (Hive warns); a child that would adopt a new task or run is refused. The v2 child prompt therefore carries no route-snapshot footer: it is the authored prompt (earlier generated footers and briefs removed) plus, for an eligible Forager, the task brief. A call that returns successfully for a child it did not bind at that progress update fails with an error naming the child; Hive does not bind the child after it ran. Fresh children need no read client.

Primary sessions get the same entry from their own route and constraints: Hive writes it when a prompt is admitted, when the session is forked (a fork's copy of its parent's entry is removed unless Hive holds a route or constraints for the fork), and right after a completed `hive_feature_select` or `hive_constraints_*` call; a session with no selected route and no constraints has no entry. The host keeps the entry in every request, compaction included, so no model request reads `.hive`. The entry holds only the route, constraints and binding, never Worklog text, task status, checkouts, explorations or live children. A failure to read `.hive` or write the entry warns and leaves the previous entry. V1 keeps the route-snapshot footer in the child prompt.

A call with `sessionID` continues a child, and Hive admits it only when every check below holds; otherwise the call fails before the host switches or prompts the child. A `sessionID` that reaches Hive's wrapper blank, holding whitespace, or as the bare `ses` or `ses_` prefix is refused first (OpenCode's native input-repair hook may normalize an optional `""` before the wrapper runs), before reservation or target preflight; a primary's refusal points to `hive_background_status({ includeSettled: true })` for the exact IDs, a child's to copying the ID from the result that reported it, and both to omitting `sessionID` for a fresh call:

- The target agent is resumable: `forager-worker`, `forager-investigator`, `architect-planner`, a custom agent derived from one of them, native `general`, or an unmanaged agent. Every other Hive role, including `scout-researcher`, the reviewers, `approach-advisor` and `hive-helper`, and native `explore` are one-shot. This check runs before any host read.
- The child is a native child of the caller in this location, its Hive binding (when it has one) names no other parent, and it runs the same agent. For a Hive-managed agent with an effective configured model, the child's session model equals that model.
- The child's binding fits the route captured when the call started: the same project, the same feature (a child bound to no feature may continue under one, unless it is bound to an ad-hoc run), and a marker that does not conflict. A marker Hive cannot resolve is refused. A resolved marker that names another task or run than the child's binding is refused; one that names a task or run for a child bound to none adopts it. A follow-up without a marker keeps the child's stored task or run, and a Forager follow-up without a marker gets the task brief of the stored task.
- The child has settled. Every continuation, including adopting an existing native direct child whose Hive binding is missing or has no parent, requires a working reader (the `server` option, or the managed local service when it is omitted), because the host joins a follow-up to the child's current run. The verified reader reads the host's own signals in the order work moves between them: any job the host still lists for the child or its descendants (running, or settled with a report not yet delivered to its owner), then the child's session tree read through the session list, the queued inbox items of every session in that tree, and their active executions. Any work, or a signal that cannot be read or has the wrong shape, refuses the continuation.

The refusal's advice depends on the failed check:

- A role, agent, model, project, feature or conflicting-marker mismatch advises starting a fresh call without `sessionID`.
- A marker Hive cannot resolve advises naming the child's own task or run, or omitting the marker line.
- A child that has not settled is refused with advice to wait for its final report, and a child whose settlement cannot be read is refused because continuation needs a settled child. In both cases wait or inspect instead of launching an overlapping writer.

The parent's route and the child's binding are read without the session index's reset-on-corruption path, so an unreadable index refuses the continuation and is left as found. The agent, model, binding and settlement checks run again at the progress barrier, after any permission prompt the host awaited, so a child that started work or changed binding in between is not prompted. Between the preflight and the barrier, while a permission prompt waits, another client (or an unmanaged call's `model`) can still change the child; there is no atomic fence against another client starting work for the same child. One activation-local reservation per child precedes the awaited reads and releases on every exit; a second call for a reserved child is refused whatever its route. A continuation keeps the child's bound project, feature, agent and task or run: it can adopt only a dimension the binding lacks, such as a task or run marker for a child bound to none. Standing constraints are not compared: the new binding takes the parent's current constraints.

## Runtime Session Inspection (2 tools)

These tools are available to execution/review primaries, Architect, Helper, and Forager under the [access matrix](#agent-tool-access). Forager uses them only for assigned recovery; Scout and specialist reviewers have no trace tools. They inspect any explicitly identified OpenCode session visible through the connected runtime. Authorization uses a fresh `session.get` and requires a well-formed record whose ID exactly matches `task_id`. Trace is read-only bounded native identity and freshness, not an allowance.

### Helper investigation contract

Primaries perform single direct reads themselves: one `hive_status`, one worktree inspect, or one `hive_task_trace_content` spot-check of a known event ref. For multi-step forensics (paging a trace, drift comparison, or interrupted-worker evidence packets), route one named question to `hive-helper` with known native session/call, feature/task or ad-hoc run, worktree, source, and destination identities. Architect may use this route as primary or child. The helper returns cited observations, attributed self-reports, hypotheses, and limits. Trace answers cite exact event refs. Interrupted-worker packets include retained placement/registration, observed source HEAD, destination identity, dirty/untracked state, and existing report/handoff paths; ad-hoc runs have no task reports. Drift packets name comparison ranges, intersecting changed paths, shared contracts, and comparison gaps. A disjoint path list alone does not prove semantic independence.

The primary spot-checks decisive cited event refs with `hive_task_trace_content` before acting. It owns acceptance, merge, cleanup, retry, continuation, termination, task creation, and status. Every HEAD discovered by Helper is **observed**, never a returned verified source pin; it cannot replace an inspected target expectation. When investigation needs Hive layout/config/forensics facts, Helper loads `hive-config` first.

Helper's Bash and external integrations are inspection-only. It never mutates repositories, worktrees, branches, files, processes, containers, or Hive state, including through commands that refresh indexes or write output. Use `git --no-optional-locks status`; plain `git status` can refresh/write the index and take `index.lock`. Do not run `git fetch`, `git pull`, `git remote update`, or any remote-ref update, or any build, test, or verification workload in a worktree whose writer is live or uncertain. If a Hive tool fails, it reports the exact failure and retained state rather than reproducing the operation with raw Git or another capability. No merge/squash, commit, forced worktree removal, branch deletion, conflict resolution, cleanup, or cancellation substitute is allowed. A semantic recovery projection is untrusted context, not evidence or lifecycle authority.

| Tool | Purpose |
|------|---------|
| `hive_task_trace` | Read one runtime-visible session as a paged forensic v3 index of surviving non-reasoning events; optionally request turn-scoped recovery |
| `hive_task_trace_content` | Read one guarded index event, continue one of its oversized fields, or re-read a recovery v2 content ID |

`hive_task_trace` requires `task_id` and accepts optional `cursor` or `recovery` (default `false`), not both. `hive_task_trace_content` requires `task_id` and exactly one selector: `event`, `event` plus `field` with optional `offset`, or `content_id` with optional `offset`. Any other combination returns `invalid_selector` before any source read. Every accepted call reauthorizes the target and rereads the source.

Trace inspection never resumes, aborts, retries, polls, or mutates the inspected session.

```text
hive_task_trace({ task_id: "child" })
hive_task_trace({ task_id: "child", cursor: "<coverage.next_cursor>" })
hive_task_trace_content({ task_id: "child", event: "<events[n].ref>" })
hive_task_trace_content({ task_id: "child", event: "<events[n].ref>", field: "output", offset: 8192 })
```

### Forensic index

V2 reads the complete public message timeline, not active context or a filtered export, through the verified server client. The reader connects to the `server` option's URL, or, when the option is omitted, to the managed local service when its registration names this plugin's own process; a missing, foreign or malformed registration means `not_configured` and no request. The [v2 options](../README.md#options) state when the registration is read and what it must contain. Either way the reader binds the exact activation/location using its held nonce, and both identity checks bracket each read. An explicit `server` never falls back to the managed service. Placement is independent of native relationship: self, child, descendant and other are classified without rerouting another location. Non-direct-child recovery stays inspect-only. Native `subagent` rows use their recorded `sessionID` metadata for child disclosure.

When verified read access fails, the `read_access` string names a connection or caller boundary: `not_configured`, `unauthorized`, `unreachable`, `wrong_location`, `wrong_instance`, `caller_unavailable` or `caller_displaced`. Target failures such as `target_unavailable` and `inconsistent_lookup` return `unavailable_or_unauthorized` without `read_access` to avoid disclosing target details. Missing configuration is not an empty timeline or confirmed idle.

When the target authorizes but its history cannot be read, both tools return `{ ok: false, reason: "source_unavailable", source_read }` on both hosts. `source_read` is `malformed` (a record or page without the expected shape), `torn` (pages that do not form one timeline, including a v2 tail that kept moving past its follow bound), `page_limit` (a v2 timeline longer than 1,000 pages of 200 messages), or `read_failed` (the read itself failed). A v2 `read_access` code appears beside it only for the connection or caller boundaries listed above. A `torn` or `read_failed` read may succeed when called again. `source_unavailable` is not evidence that the history is empty or that the session is idle. Configure the URL and password environment-variable reference in the **server process**; custom variables may also reach trusted tool subprocesses. The reader cannot guess a server or start one.

Each page lists events in source order under a 24 KiB budget (`render.bytes` is exact) and always makes forward progress. An event is one text, tool, retry, patch, compaction, or unsupported part, or an assistant message error. Step markers are counted as `source.structural_parts`. Reasoning is excluded from events, refs, cursors, guards, and errors; `reasoning` reports only part, byte, and token counts.

Each row carries `seq`, `kind`, `actor`, and, where recorded, `tool`, `status`, `call_id`, and `title`. Tool rows show the complete `input` when it is small; otherwise they show the recorded identifying keys that are present (`description`, `command`, `filePath`, `path`, `pattern`, `name`, `url`, `query`, `subagent_type`). Text, output, and error excerpts keep a head and a tail around ` [...] `, so commands and outputs that share a long prefix stay distinguishable. `bytes` gives the canonical size of each present field; a field missing from `bytes` is absent. `abbreviated` names every displayed value that is not complete, including long tool names, titles, types, and call IDs.

A native `task` call row also carries `child_session_id` when the call recorded exactly one valid child ID (in `state.metadata.sessionId`, optionally mirrored in part metadata) and a fresh `session.get` confirms that session exists with the traced session as its parent. Each read checks the distinct candidates on the displayed page or selected event again. A missing, malformed, conflicting, or unconfirmed identity shows no field, and raw metadata is never shown. The recorded identity is part of the event guard, so a ref stops resolving when it changes.

`context.assignment` is the first user-authored text. Host-generated user text (v1 text parts marked `synthetic`, such as attachment expansions and continuation prompts, and v2 `synthetic` messages) is skipped; when a session records only such text, its first one is shown with `synthetic: true`. `context.final` is the terminal assistant text for a terminal lifecycle and is a `child_self_report`, not proof. Both link to their event with `ref` when the event has one and carry `identity` like index rows.

`coverage.next_cursor` continues the index. Pass the entire string unchanged as `cursor`; read one event's detail by passing that row's `events[n].ref` as `event` to `hive_task_trace_content`. The cursor is a readable string of the form `trace-cursor:v3:<scope>:<after_seq>:<guard>`. `scope` is `prefix` or `source`, `after_seq` is the last `seq` already returned, and `guard` is the complete 43-character SHA-256 digest. Callers do not decode or rebuild it. A copy that no longer has this form, such as a shortened or padded one, returns `invalid_cursor` with a `hint`, and an edited copy that keeps the form but no longer matches its guard returns `cursor_stale`; omit `cursor` to restart from the first page. Cursors issued before this form (a base64url encoding of a four-element JSON array) are still accepted when valid. After `cursor_stale`, restart from the first page. A `prefix` cursor guards the native-identity chain of the events already returned. When every event up to the cursor has native identity, the cursor accepts appended events and returns `cursor_stale` when any earlier eligible event was inserted, deleted, or changed. When any of those events lacks native identity, the cursor is a `source` cursor and any change to the eligible source returns `cursor_stale`, including an append, because deleting one of several identical events would otherwise go undetected. `coverage.complete: true` means the pages from the first to this one covered every eligible event in the surviving source as observed. It is not evidence about history the runtime no longer holds or about the filesystem. `coverage.limitations` lists `compacted_source`, `compacted_tool_output` (rows marked `compacted`), `unsupported_parts` (rows with `kind: "unsupported"` and only a bounded `type`), and `positional_identity` (rows marked `identity: "positional"` or `"ambiguous"`).

### Event reads

`hive_task_trace_content({ task_id, event })` returns the selected event with native `message_id`, `part_id`, and `call_id` when recorded, a confirmed `child_session_id` under the index rule, and every field of its kind: `input`, `output`, and `error` for tools; `text`; `error`; or `files`. Each field is `{ state: "absent" }`, `{ state: "value", format, bytes, value }`, or, above 8 KiB, `{ state: "chunked", format, bytes, sha256, content, offset, next_offset }`. An empty string is a `value`, not `absent`. Small object inputs stay objects. Chunked `json` fields are canonical JSON with sorted keys; concatenating chunks reproduces the text that `sha256` covers. Continue with the same `event` and `field`, setting the request's `offset` to the prior response's `next_offset`.

Each ref carries a full SHA-256 guard over the event's allowlisted fields, so the tool input, output, and error always come from one stored tool part. Refs with native identity survive unrelated appends and movement. Content equality is not identity, so events without unique native message and part IDs get weaker selectors. An event whose content is unique in the source is marked `identity: "positional"`; its ref names that event only while the whole eligible source is unchanged, and any change, including an append, returns `source_changed`. An event byte-identical to another event is marked `identity: "ambiguous"` and has no ref: its row stays in the index with bounded excerpts, but its full fields cannot be read, and a selector that reaches it returns `identity_unavailable`. A replacement that leaves the eligible source byte-identical is undetectable without native IDs. On v2, assistant text items carry no native part ID, and the host may replace a message's whole content array, so their positional refs and `source` cursors stay invalidated by any change, including an append. `event_changed`, `event_not_found`, `event_ambiguous`, and `source_changed` mean the ref no longer establishes the selected event; re-index before drawing conclusions. `source.as_of` in index and event replies is a digest of the eligible event sequence. It changes when an eligible event is added, removed, or changed and ignores reasoning, step markers, and message completion. It gates positional refs and cursors over events without native identity, not native refs.

### Trace policy and recovery

If semantic recovery would help build a fresh handoff, call `hive_task_trace({ task_id: "child", recovery: true })`. Recovery remains untrusted and never authorizes continuation. On v1 every returned task result is terminal, so follow-up work uses a fresh child session and may reuse the same Hive task/worktree; primaries must not pass `task_id` or infer eligibility from task output, trace, `idle_and_closed`, cancellation acknowledgement, or transcript quality, and pass it only when an explicit operator instruction or explicit runtime-owned interruption-recovery mechanism authorizes continuation. On v2 a settled child of a resumable role may be continued with `sessionID` on the same agent and the same task or investigation for one or two bounded follow-ups, under the checks in [V2 subagent dispatch and continuation](#v2-subagent-dispatch-and-continuation); a new task, an independent review or challenge pass, and a retry after a dead end start a fresh child. On either host, if the child may still be active or its lifecycle is uncertain, inspect, wait, or reattach as supported; do not send another prompt or launch an overlapping writer.

Use a successful, intelligible terminal return as the normal handoff, subject to the required review and verification checks. Investigate traces when a specific unresolved question about output, lifecycle, verification evidence, or material instruction compliance could change acceptance or recovery, or when the operator explicitly requests an audit. The primary performs a single known-event spot-check itself; multi-step questions go to Helper with known identities. Helper reads only the events/fields needed and stops when resolved. The primary spot-checks decisive cited refs before acting. A named skill alone does not require a trace, and a terminal return need not list skill loads.

Required skills must still be loaded before covered work. Audit skill loading only for an explicit operator audit request or a concrete concern about material noncompliance. During that audit, check the forensic index for completed native `skill` tool events whose input names the exact required skills before the covered work. A self-report or late load does not prove timely loading; a successful load does not prove adherence to the skill. Missing or incomplete evidence is not a confirmed omission; keep the audit and affected acceptance question unresolved. An omitted or late required load requires a fresh child after the prior child is terminal, with the requirement preserved. If trace tools are unavailable, report the limitation and keep the affected acceptance question unresolved.

Recovery output keeps its v2 projection. Its 24 KiB soft target is advisory, not a cap, and `render.actual_bytes` is exact. Its `content_id` values stay readable through `hive_task_trace_content({ task_id, content_id })`.

Recovery treats every user message as closed input on both hosts, although a v1 user record has no completion time. An assistant message error belongs to the last step of its message, after that message's work, as `assistant_error` follows the message's parts in the index; a message with no other parts gets a step of its own. `task_instruction` is the latest user-authored text under the same rule as `context.assignment`, and carries `synthetic: true` only when the session records no user-authored text. `source.compactions` counts each compaction once: v1 records one compaction as a request message with a `compaction` part and a summary message whose `parentID` names that request, and a summary without a recorded request counts by itself.

`lifecycle` carries `state`, `terminal`, `reason`, and what was observed. `runtime` is the target's status in the runtime instance for the directory recorded on the target session: `busy`, `retry`, `idle`, or `unavailable`. Source and status are read from that directory, not the caller's project. A target without a valid absolute directory reports `placement_unavailable` and is never treated as idle. A missing target entry in a valid status map means idle because OpenCode removes idle entries; an unavailable or invalid map reports `status_unavailable`. On v2 `runtime` comes from the whole session tree instead: the target is `busy` while any job the host lists for it or its descendants, any queued inbox input, or any active execution remains anywhere in its tree, so a session that is idle while its backgrounded `shell` command or a descendant still works reads as busy, and it is `idle` only when the tree has settled. A settlement that cannot be read reports `status_unavailable`. `unresolved_tools`, present when nonzero, counts pending or running tool records in the latest message and in earlier messages.

Any unresolved tool record or open latest assistant message keeps `terminal: false`, even when `runtime` is `idle`. A host restart leaves exactly that shape: the new instance does not know the old turn, so it reports idle, while the stored records still show work without a result. Idle status in the current instance says nothing about subprocesses or other effects the old worker started. `idle_and_closed` means only that the observed latest turn finished. It is not a completion check over the whole history: an earlier assistant message left open without an unresolved tool record does not block it, and it says nothing about effects started in earlier turns.

`recovery.scope` names what a recovery covered. `closed_turn` is the normal projection for an `idle_and_closed` lifecycle. `evidence_only` covers an `idle` runtime whose `reason` is `tool_pending_or_running` or `latest_assistant_open`. An evidence-only snapshot keeps `lifecycle.terminal: false` and `final_response: null`, and its `semantic.safest_next_action.action` is always `inspect`, whatever the summarizer proposed. It helps decide what to inspect; it is not execution authority and does not show that the child stopped. Recovery is refused with `scope: null` for active (`busy` or `retry`), `status_unavailable`, `placement_unavailable`, self, empty, and other uncertain lifecycles. After summarizing, recovery resolves the target again and rereads its placement, source, and status. A lost authorization, a changed parent (compared exactly, so a move between two foreign parents counts) or directory, changed source, active or unavailable status, or a changed lifecycle discards the result with a `freshness` failure. `recovery.status: "complete"` means the summary covered the surviving source, not that the task completed.

Summarizer requests carry a per-stage output contract built from the same strict schema that validates the reply. Map replies are `{ kind: "map", range, cards }` and reduce replies are `{ kind: "reduce", semantic }`; unknown or missing keys, blank strings, and wrong ranges are rejected. A malformed map card falls back on its own step while valid sibling cards are kept. A step with neither observed evidence nor plaintext reasoning takes the explicit all-empty card. An unfinished claim must cite at least one step that has observed evidence or plaintext reasoning, and a completed claim must cite at least one such assistant step, which the reduce request lists as `completion_steps`; a user request can support an unfinished claim but never a completed one. A claim citing only unsupported steps fails reduce validation, and a recovery with no such assistant step always proposes `inspect`. The configured variant is validated against provider metadata and never claimed as applied when unavailable; `recovery.model.observed` comes from the host's response. A provider error, absent or unparseable text, or a request above the model input budget (including the contract) falls back deterministically. Failure entries may include at most four value-free `diagnostics`, never provider messages, bodies, source text, or model text. Cleanup of ephemeral sessions is always attempted under bounded deadlines; a cleanup failure is reported and any session ID whose deletion is unconfirmed is retained. There is no model fallback or automatic retry.

Semantic output is always `untrusted: true`. Generated `source_steps` arrays are sorted context source coverage, not evidence or proof. Never accept, merge, retry, resume, or auto-run from recovery output.

Ordinary v1 trace/content cancellation behavior is unchanged. Ordinary v2 trace/content reads stop with the calling invocation, including identity, relationship, paging and status requests. Recovery reads/generation cancel with the caller on both hosts; cleanup uses independent bounded deadlines.

For v2 recovery, the plugin allocates the summarizer ID before public `session.create({ id })`, excludes the target ID before ownership/create, and keeps allocated IDs cleanup-owned even if creation commits before returning. Cleanup waits for an unsettled create within its 10-second deadline. Native `Session.NotFoundError` or `SessionNotFoundError` confirms absence. A create that commits after that window can leave a known unconfirmed ID; there is no later sweeper. When a create returns a session ID other than the allocated one, Hive cleans up the allocated session as usual, never generates in or removes the returned session, and records the returned ID as unconfirmed with `ephemeral_cleanup_failed`. Live failures report `ephemeral_cleanup_failed`; interrupted callers retain unconfirmed IDs in activation-local accounting. V1's acquisition behavior remains unchanged.

Each recovery binds one model selection when it starts and uses it for the model metadata and every map and reduce request. With no `taskTraceSummarizer` model, the selection is the invoking caller session's current native model and variant, read without changing that session; a v2 caller session without its own model is bound as the OpenCode 2.4.1 runner selects it: its agent's effective configured model and variant when the host lists that model as available, otherwise the host default model with no variant, and that default only when it names a provider package, since the runner otherwise picks another model that Hive does not reproduce. A session that names no agent runs on the default agent; Hive takes that agent from the one the host names for the `hive_task_trace` call, and when neither names an agent the selection is not established. A plugin's `experimental.model.resolve` hook can still redirect the request; the observed model records what ran. A configured `model` alone replaces the caller's model and uses that model's default variant; a configured `model` and `variant` replace both. Configuration validation rejects a `variant` without a `model`. If the caller's selection cannot be established, recovery returns `status: "unavailable"` with a `model`-stage `summarizer_unavailable` failure and the `caller_model_unavailable` diagnostic, and no session is created; Hive never substitutes a guessed model. `recovery.model.requested` reports the bound `model`, `variant` and its `source` (`caller` or `configured`). Unsupported variants produce `variant_unavailable` before creating a session, rather than silently dropping the request. Hive sets no request options such as temperature on summarizer requests. Observed model/variant comes from the actual native generation (the v2 `generate` hook, or the v1 reply info). Provider-internal retries are not claimed controlled by Hive.

### Children after a restart

On v2 every `subagent()` call returns `running` with the child's `sessionID` at once, so the parent holds the child ID from the launch receipt. When a launch call ended before it returned the `sessionID`, `hive_background_status({ includeSettled: true })` lists every direct child of the caller, idle ones included (without `includeSettled` the list omits children with no observed work); then `hive_background_status({ sessionID })` reads whether that child's whole tree has settled. When more than one listed child fits the lost launch, its identity stays unresolved. On v1 a `task()` call blocks, and Hive keeps no record of its child. When a host restart ends a v1 call before it returns, the parent's stored call keeps `running` or `pending` status and the parent never received the child ID in a result. These paths can name the child:

- On v1 only, on each later turn, the runtime adds a replay hint to the parent's call naming `hive_task_trace({ task_id })` for the child. The hint says the call has no recorded result and the child may still be in flight. Hints are rebuilt for every turn. Only a child's newest recorded call decides its hint, so a later result for the same child supersedes an older call that has none. Hints cover up to the eight newest children whose newest call needs one, and skip a call that is still the latest message, background launches (`background: true` in the call's recorded metadata or input), and children the runtime does not confirm as direct children of that parent. Empty and terminally unsuccessful foreground task results get the same kind of hint.
- `hive_task_trace` on the parent session (self inspection is allowed) shows `child_session_id` on a parent's native call row (`task` on v1, `subagent` on v2) only when the stored call records the child's session ID in its metadata and the runtime confirms that child belongs to the parent. On v2.4.1 a `subagent()` call stores the child's `sessionID` in its metadata when it returns; a call a restart ended before it returned may show no `child_session_id`, though `hive_background_status({ includeSettled: true })` still lists the child among the caller's direct children.

Use these paths instead of runtime exports or `.hive/sessions.json`; neither is a trace source. When neither path names the child, its identity stays unresolved; a missing child ID does not show that the child stopped, so wait, ask, or keep inspecting instead of launching a replacement writer. When a path names the child, trace it, and treat its lifecycle and any evidence-only snapshot under the rules above before deciding to wait, ask, or launch fresh.

Configure an optional recovery model under global `taskTraceSummarizer` (`model`, and `variant` only with `model`). Operator reference: [Task trace summarizer](../README.md#task-trace-summarizer).

## Context (5 tools)

| Tool | Purpose |
|------|---------|
| `hive_context_read` | Read a scoped summary, bounded durable catalog, or chunked exact document |
| `hive_context_write` | Explicitly create a scoped file, or replace one whole document with revision and hash preconditions |
| `hive_context_append` | Append a dated block while preserving prior bytes and checking revision plus content hash |
| `hive_context_edit` | Replace one exact passage of an existing file, keeping every other byte, with revision and hash preconditions |
| `hive_context_archive` | Selectively archive named files with a reason, revision, and per-name hashes |

All five context tools accept optional `scope: 'feature' | 'project'` (default `feature`) and optional `feature` for feature scope. Read also accepts `name`, `view: 'summary' | 'catalog'`, `query`, `limit`, `cursor`, `maxBytes`, and `scanChars`, subject to the view restrictions below. Write requires `name` and `content`, with optional `kind`, `task`, `expectedRevision`, and `expectedContentHash`; omit the preconditions only when creating a missing file. Append requires `name`, `content`, `expectedRevision`, and `expectedContentHash`, with optional `section` and `task`. Edit requires `name`, `oldText`, `newText`, `expectedRevision`, and `expectedContentHash`, and takes no `kind`, `task`, or section option. Archive requires `names`, `reason`, `expectedRevision`, and `expectedContentHashes`.

Omitted `scope` retains feature-default behavior. Use `scope: "project"` explicitly for `.hive/context/`. Tool scope selects data. Foragers and reviewers write feature and project context through revision and content-hash checks. Scouts are read-only. Archive is primary-only.

With no `name`, `hive_context_read` defaults to `view: "summary"`. Use `view: "catalog"` with optional literal `query`, `limit`, and returned `cursor` for durable metadata discovery. Named reads accept `cursor` and `maxBytes`, return `range: { startByte, endByte, totalBytes }`, `complete`, and `nextCursor`. `maxBytes` defaults to 16 KiB and cannot exceed 64 KiB. A named-read response lists `scope`, `revision`, `snapshot`, `range`, `complete` and `nextCursor` first and `file` last; inside `file`, `contentHash` and the metadata precede `content`, so the guard appears before a long body. `file.contentHash` is the whole-file hash that mutations take as `expectedContentHash`; the top-level `snapshot` is a different value and is not accepted as a guard.

For shared contracts, repository-wide conventions, or cross-feature decisions, permitted non-isolated agents consult the project catalog alongside relevant feature context. Catalog `task` associations are relevance hints, not filters or authority. See [context-engineering](../skills/context-engineering/SKILL.md) for selective reads and review isolation.

A named read pages through one document. Its `nextCursor` binds the document, scope, revision and content hash, so a cursor from another document, an earlier revision or another activation fails as `stale_context_cursor`; restart the read. Finish the chunks (`complete: true`) before replacing a document, because a partial read does not cover the whole file. Creating a name that exists fails with `context_already_exists`. On `context_index_invalid` or `context_reconciliation_required`, stop managed mutations and report the actual error; reading about repair does not authorize an agent to edit Hive control files.

Feature-scope writes, appends, edits and archives need an existing feature with readable `feature.json`. An unknown, ambiguous or unreadable feature name fails with the feature resolution error (`Feature '<name>' not found` for an unknown one) before any directory or lock is created, and malformed names, content, hashes, kinds and archive arguments are refused before storage is created where the arguments alone decide them. Reads of an unknown feature still return empty context. Each publication holds the context lock and keeps a pending marker until it finishes. A lock-free read that meets a running publication's marker fails `context_changed_during_read`, which means retry the read. Reads and mutations report `context_reconciliation_required` only when the marker outlived its writer: the operating system reported the lock free while the same marker file remained. A lock file left by a host that predates native locking does not count as a live writer. The tools never remove the marker or repair the index.

`hive_context_edit` changes one passage without reproducing the rest. The caller's own named read needs to show the whole passage and enough surrounding text to justify the change; unrelated chunks may stay unread. Every chunk carries the whole-file hash, so the revision and hash guards refuse a document that changed after the read, but they do not show what unread bytes say. Under the context lock the service checks the revision, then the hash, then requires `oldText` to occur exactly once as literal UTF-8 bytes, counting overlapping occurrences. It splices `newText` between the untouched prefix and suffix bytes, so BOM, CRLF, Unicode and replacement patterns such as `$&` are preserved as written. Failures are `context_not_found` (no namespace is created), `context_edit_no_match` (the message names CRLF when the document has it), `context_edit_ambiguous`, `context_edit_no_change` for identical text, `invalid_argument` for empty `oldText` or an unpaired surrogate, `context_invalid_utf8`, `context_input_too_large` when an operand or the edited document exceeds 1 MiB, and `invalid_context_metadata`. Each is refused before publication and writes nothing. Empty `newText` deletes the passage; evidence and reserved files may become empty, while durable files keep their required metadata. The edit keeps the index kind, task and `createdAt`, advances the revision once and returns the same result shape as write. After an error or unknown result, read and confirm whether the edit applied before retrying: an identical retry after success fails `stale_revision`, a blind replay can apply twice when `newText` contains `oldText`, and seeing `newText` does not prove this call applied it. The lock and guards cover writers that use the context tools; a direct file write during publication is outside that guarantee, and a publication error restores the prior bytes or leaves the pending marker, after which managed mutations report `context_reconciliation_required`.

Call `hive_context_read` before replacement, edit, append, or archive. Existing-content mutations require the current revision and actual SHA-256 `contentHash`.

`expectedContentHash` (and each `expectedContentHashes` value) must be the named read's `file.contentHash` copied verbatim: 64 lowercase hexadecimal characters. The argument schema types the guard as a plain string with no pattern or length, so any string reaches the service and its message, not generic host validation, explains the problem. A required guard that is missing or not a string never reaches the service: the host's native argument validation rejects the call with its own message. For archive that covers a non-string map value; a name absent from `expectedContentHashes` does reach the service and is reported as missing under `expectedContentHashes["<name>"]`. For `hive_context_write`, where both guards are optional, supplying only `expectedContentHash` or only `expectedRevision` fails `context_precondition_required` at the tool before it chooses create or replace, so a half-specified replacement never creates a missing document; omit both to create and pass both to replace. A string of the wrong length or with characters outside lowercase hex fails `context_precondition_required` with a message that names the field, the required form and what arrived (its length, or that it is not lowercase hex) and states that nothing was written; do not pad, trim or otherwise repair the rejected value. The service still rejects a missing or non-string guard the same way for callers that bypass the tool schema. The same reason also covers a missing or invalid `expectedRevision` (that message names `expectedRevision`, requires a nonnegative safe integer from a fresh named read, says what arrived and states that nothing was written) and a missing archive hash map, so act on what the message says rather than on the reason code alone. A well-formed value that does not match the current bytes fails `stale_content`; the message says the file changed after the read or the value was not copied exactly, states that nothing was written, and does not reveal the current hash. Recovery from either hash refusal is the same: make a fresh named read and rebuild the intended change from it, reading every chunk before a whole-document replacement or the passage and enough surrounding text for a bounded edit, then pass that read's revision and `file.contentHash`. Resending content built from the earlier read under the new hash discards whatever changed. Both messages are complete in `Error.message`, which is all a v1 or v2 host shows the caller; the `reason` code is not needed to recover. Non-reserved files default to `durable`. Mark raw logs and historical verification material as `evidence`. Feature hygiene warnings begin above 8 durable files or 40,000 UTF-16 code units; project warnings begin above 32 files or 160,000 units. These are review signals, not aggregate admission limits.

`overview`, `draft`, and `execution-decisions` are reserved and excluded from the durable catalog and durable-context hygiene counts. `overview` keeps a feature's purpose and design summary and `execution-decisions` the reasoning behind orchestration choices; progress, revision history, and routine execution narration go to the [Worklog](#worklog-3-tools). They remain readable by name. They do not accept a caller-provided `kind`; the per-document size limit still applies. Plan approval does not archive `draft`. Archive an obsolete draft explicitly after approval.

## Worklog (3 tools)

| Tool | Purpose |
|------|---------|
| `hive_worklog_list` | List feature and session Worklogs from their storage files, newest first |
| `hive_worklog_read` | Read one Worklog's brief, history, or recorded-facts view |
| `hive_worklog_record` | Append one checkpoint, optionally replacing the current briefing in the same commit |

A Worklog is a short account of where work stands: a current briefing a reader can absorb in about thirty seconds, plus append-only checkpoints. Each feature has one log shared by every primary session; ad-hoc work uses the calling session's own log under its host owner. Reads also project recorded task facts from `status.json` files, which describe stored state only. The service contract, including storage, limits and every failure reason, is [docs/WORKLOG.md](../../../docs/WORKLOG.md); results are the core result shapes unchanged, so each names its resolved `ref` and `key`.

- `hive_worklog_list` takes optional `kind` (`feature` or `session`), `limit`, `cursor`, and `maxBytes`. It reads the fixed storage locations, not the session index, so completed and archived features and ended sessions stay listed.
- `hive_worklog_read` takes optional `ref`, `view` (`brief` default, `history`, `facts`), `limit`, `cursor`, and `maxBytes`. Without `ref` it reads the feature selected for the calling session with `hive_feature_select`, or the caller's own session log when the route is unset or null. It never uses the detected-worktree or sole-live-feature fallback that feature-scoped task tools apply, because a narrative written into the wrong shared log cannot be deleted. A selected feature that no longer resolves fails with `feature_not_found` rather than reading the session log. The session index is read without its reset-on-corruption path, so an unreadable index fails the call and stays unchanged; an explicit `ref` needs no index. A missing log reads as `exists: false` with revision 0. Reads never write.
- `hive_worklog_record` requires `ref`, `operationId`, and `checkpoint` (`summary`, optional `detail`, `references`, `corrects`), with optional `title`, and `briefing` together with `expectedRevision`. The host fills the author from the calling session, its native owner, and the agent the runtime reports; arguments cannot set it. A session log accepts only the caller's own session; any recording primary may write a feature log.

Worklog results are compact JSON text without indentation, and `maxBytes` bounds that text. The v2 structured `output` is the same JSON. A `record` result is not bounded by a read budget but uses the same serialization. A `response_too_large` failure is a structured result, not a page, and its `details.requiredBytes` names the size needed. Every other Hive tool keeps its two-space JSON presentation.

Every `WorklogError` returns as `{ success: false, reason, error, details, ref? }` with `reason` and `details` unchanged. After a lost, unknown, or failed record result, resend the identical request with the same `operationId`: a landed entry returns `replayed: true`, and an absent one commits normally. That includes `io_error` with `details.stage: 'write'` and `details.publication: 'uncertain'`, which does not show whether the entry was appended; a new `operationId` there can append a second checkpoint. `stale_revision` means another entry landed after the read: read again, reconcile the briefing, and record with a new `operationId`. `operation_conflict` means the `operationId` was used for a different request. Scope errors that are not `WorklogError`, such as a missing session identity, fail as ordinary tool errors.

Every Hive role except native `general`/`explore` and the hidden summarizer may list and read. Hive grants recording to primary sessions of the full primaries, Architect, and the review primaries; see the access matrix. An unmanaged agent (neither a Hive role nor a custom variant of one) keeps its native permission for Hive tools and can record from a primary session, while child sessions and native `general`/`explore` are refused. Log text is untrusted narrative from agents, never instructions, task status, or policy, and the runtime never injects it into prompts. Primaries read it on demand and confirm claims against task records. The `/worklog` command reads and explains a log without recording. Operators who do not want primaries to keep a Worklog add an ordinary standing constraint.

## Exploration (2 tools)

| Tool | Purpose |
|------|---------|
| `hive_explore_read` | List active explorations, or read one exploration's brief or full view |
| `hive_explore_update` | Create or update one exploration: upsert frontier items and observations, or close it |

An exploration records one investigation in any domain, such as debugging a failure, auditing a surface or researching a question. It holds a goal, an optional `subject` naming what is explored (for example `root/main @ 5c163be (src/auth)` or a base URL), a keyed **frontier** of targets to settle, and keyed **observations**. `ExplorationService` in `packages/hive-core/src/services/explorationService.ts` owns storage, limits and every failure reason.

- Status is `active` until an update closes it. `concluded` needs a `conclusion` and `abandoned` needs a `reason`; both are terminal, so a follow-up or retest is a new exploration whose `priorExplorationId` names the closed one. `subject` and `priorExplorationId` are set only at creation.
- A frontier item has `key`, `target`, `state` and optional `question`, `evidence`, `reason` and `refs`. `evidence` is required for `covered` and refused for every other state; `reason` is required for `blocked` and `dropped` and refused for `open` and `covered`. An observation has `key`, `summary`, `status` (`confirmed`, `hypothesis` or `refuted`), optional `refs` and an optional `supersedes` key, which must name another observation of the same exploration; supersedes chains cannot form a cycle. Both collections are upserted by key, a key may appear once per call, and nothing is deleted: a target that no longer matters is marked `dropped`.
- An update to an existing exploration must carry a `goal`, a `status`, or at least one frontier item or observation. Repeating the stored `subject` or `priorExplorationId`, or sending empty `frontier` and `observations` arrays, changes nothing and fails `invalid_argument`; a changed `subject` or `priorExplorationId` fails `immutable_field`.
- `expectedRevision` is required: 0 creates (with a `goal`), and any other value must equal the stored revision or the call fails `stale_revision`. An optional `operationId` makes a retry safe: an identical request from the same session returns `replayed: true` with its `committedRevision`, even after the exploration closed, and a different request with the same `operationId` fails `operation_conflict`. The 32 most recent receipts are kept.
- Reads compute `scopeMapped` (the frontier has items), `counts`, `gaps` (open and blocked items) and `stagnantRevisions`, the revisions since the last observation change (including a changed `supersedes`) or frontier item that became covered, blocked or dropped. Adding open items or editing the goal does not reset it. None of these are stored.
- `hive_explore_read` without `id` lists active explorations, newest update first, as `{ explorations, totalActive, truncated, errors }`; an unreadable, oversized or symlinked file appears in `errors` and never fails the list. A symlinked `.hive/explorations`, `active/` or `closed/` fails the list, a named read and an update with `unsafe_path`, and one that exists but is not a directory fails them with `io_error` (`details.stage: 'path'`, `code: 'ENOTDIR'`), never as an empty list or `not_found`. With `id`, `view: 'brief'` (default) adds bounded `gaps` and `observations` lists, each `{ items, total }` with `items` a prefix of the ordered list and without evidence or refs; `view: 'full'` returns every item. List and brief results fit 16 KiB of compact JSON. The stored document is capped at 48 KiB, so the full view fits a 64 KiB response; an update that would grow an active exploration past 44 KiB fails `exploration_full`, and the remaining 4 KiB is kept so a close that adds nothing but its status, conclusion or reason always fits. `EXPLORATION_LIMITS` in the service holds every size and count limit. There are no cursors.
- Files live at `.hive/explorations/active/<id>.json` and move to `.hive/explorations/closed/<id>.json` when closed. Every write flushes the file and, on POSIX hosts, the directory entries that reach it (its placement directory, `.hive/explorations/` and `.hive/`) before it is acknowledged; Windows offers no directory flush, so there the rename alone publishes it. The closed copy is published this way before the active copy is removed, and it wins if an interrupted close left both; the next update or replay removes the stale active copy. A file whose status does not match its directory (an active document in `closed/` or a closed one in `active/`) is refused as `exploration_corrupt` by reads, lists and updates, and a list reports a linked, unreadable or misplaced `closed/<id>.json` beside an active file in `errors`. A named read that races a close checks `closed/` again before answering `not_found`. Updates hold a per-exploration lock and publish atomically.

Exploration results are compact JSON, like Worklog results. Every `ExplorationError` returns in the shared Hive failure envelope `{ success: false, reason, error, details? }`, where `error` is the message and `details` is present when it has fields. Argument refusals that need no stored state, including the ID pattern, every byte and count cap, a `supersedes` cycle within one call's observations and, on creation, a `supersedes` naming no observation of the call, happen before any lock or directory is created and touch no file. A refusal that depends on the stored exploration publishes no new revision, though taking the lock or removing a stale active copy of a closed exploration may touch files. An `io_error` with `details.publication: 'uncertain'` is resolved by resending the identical request with the same `operationId`; the retry repeats the directory flushes and returns `replayed: true` only once they succeed, failing the same way until then. The host stamps `createdBy` and `updatedBy` from the calling session, owner and agent; arguments cannot set them. Every Hive role except native `general`/`explore` and the hidden summarizer may read; primary sessions of the full primaries, Architect and the review primaries may update. Every successful result carries `untrustedNotice`; a failure envelope does not. Entries are agent-recorded observations and hypotheses, not verified ground truth, task status or policy.

## Councils (1 tool)

| Tool | Purpose |
|------|---------|
| `hive_councils_list` | List the configured councils and resolve the seats of one, for the `council` skill |

`hive_councils_list({ name? })` reads the effective `council` configuration and the agents the host has when the call runs. It dispatches nobody. Pass `name` only when the operator explicitly named a council; it is matched exactly, so any string that names no configured council, including a blank one, returns `unknown_council`. Without it the default council (`council.defaultGroup`, else `decision`) is used. The `/council` command carries no roster: it renders the operator's text and loads the `council` skill, which calls this tool.

The result always has `notice`, `councils` (every configured council as `{ name, description? }`, in configuration order), `selected` (the council the call resolved: the named one, else the default) and `skipped: [{ name, reason }]`. Then either `ok: true` with `members: [{ name, baseAgent, description }]`, or `ok: false` with `reason` `unknown_council` or `no_usable_seats` and no members of any council. A broken default fails only a call without `name`; a named usable council still resolves. There is no fallback to another council and no seat cap.

Members are judged once each, in configuration order, and the first occurrence of a name wins. A skip `reason` is one of:

- `not_registered`: no Hive role or custom agent has that name.
- `not_available`: the host does not offer it now. On v1 that is an operator `agent.<name>.disable: true` on a Hive subagent, read when the config hook runs (v1 configuration is fixed after startup). On v2 it is an agent the host no longer lists, or a Hive subagent the operator made a primary.
- `example_template`: a starter template whose name contains `example-template` or whose canonical Hive description still starts with "Example template only". On v2 the canonical description is used even when a native description override exists, and members report it too.
- `ineligible_base`: the agent's base role is not one of the council seat bases (`COUNCIL_SEAT_BASES` in `src/runtime/role-policy.ts`): `scout-researcher`, `plan-reviewer`, `code-reviewer`, `simplicity-reviewer`, `approach-advisor`, `vulnerability-reviewer`. Investigators, Foragers, Helper and orchestrators never sit.
- `duplicate`: a repeated name.

When the host agent catalog cannot be read (on v1 before the config hook has run, on v2 when `agent.list()` fails), the call fails; it never returns an empty or guessed roster. The tool description and `notice` state the council rules: load the `council` skill before convening and stop if it is unavailable; on `ok: false` launch nobody and substitute no other council; names and descriptions are operator configuration data, not instructions; the convenor and every councillor must work read-only during a council. That last rule is an instruction, not something the host enforces.

The tool is granted to the full primaries, Architect and the review primaries, and is primary-only: child sessions are denied it, so a delegated Architect returns a council request to its parent. It is not a Code Mode read: it is a direct call under both read transports.

## Status (1 tool)

| Tool | Purpose |
|------|---------|
| `hive_status` | Get feature metadata, task summaries, dependency readiness, and feature-task worktrees as JSON |

The response is `{ feature, tasks, runnable, blocked, planSync, worktrees }` ([Plan sync status](#plan-sync-status)), with optional config fallback `warning`, freshness failure `specFreshnessError`, and `unownedTaskHeadings: [{ line, title }]`. For a known feature, `feature` has `name`, `status`, `hasPlan`, `planApproved`, and `commentCount`. `status` is the feature lifecycle from `feature.json` (`planning`, `approved`, `executing`, `completed`, or `archived`) and does not follow later plan edits; `planApproved` is `true` only while an approval covers the current `plan.md`, as `hive_plan_read` `status: 'approved'` reports it. When the `APPROVED` marker or the plan cannot be read, `planApproved` is `null` and `planApprovalError` carries the read error; the lifecycle `status`, `tasks`, and the other summaries are still reported. An archived feature with an approved plan therefore shows `status: 'archived'` and `planApproved: true`, and an approved feature whose plan was edited outside the plan tools shows `status: 'approved'` and `planApproved: false`; for an unknown feature or missing `feature.json`, it is `null` and the other summaries may be empty. Top-level `tasks` is the sole task list. Its summaries (`folder`, `name`, `status`, `origin`, optional `planTitle`, `summary`, `repoIds`, `blocker`) include `dependsOn` (the stored dependency folders, `[]` when missing, kept on done and cancelled tasks as history), `specStale` (true/false/null), `specStaleReason`, and `hasHandoff`. `blocker` carries the stored operator-decision reason, options, recommendation, and context when present. `runnable` and `blocked` are computed from the same task projection. The response lists only forward edges; to find the tasks that depend on one, scan the other entries' `dependsOn`, and judge the actual impact separately. Freshness reasons: `matches_plan`, `differs_from_plan`, `manual_task`, `plan_missing`, `plan_invalid`, `task_not_in_plan`, `spec_missing`, `unowned_heading_after_task_section`, and `freshness_unavailable` when a check fails (with top-level `specFreshnessError`). `differs_from_plan` compares stored spec text with what the current plan would generate, including generator or manual-spec changes; unrelated plan sections do not affect it. `runnable` is a list of folders and `blocked` maps folders to unmet dependencies. Read `status.json`, `spec.md`, `handoff.md`, and reports for other bodies. Ad-hoc runs and live subagent children do not appear in this response.

Every retained task folder stays visible. A missing or unreadable/corrupt `status.json` yields an integrity entry `{ folder, name, status: null, integrity: { reason: 'status_missing' | 'status_unreadable', error? }, specStale, specStaleReason, hasHandoff }`. The error is present for unreadable/corrupt status. Freshness is derived by folder identity when possible, and existing specs/handoffs are retained. Integrity entries have no invented origin or dependencies, never appear in `runnable` or `blocked`, and never satisfy another task's dependency. Inspect and repair the authoritative task records before treating that folder as executable.

`worktrees` contains healthy entries. When a workspace or namespace cannot be read or validated, the response adds `worktreeErrors: [{ path, reason }]` and retains the remaining feature, task, dependency, and worktree summaries. See the manual orphan recovery procedure under [Worktree families](#worktree-families-8-tools).

### Native feature-task brief

Task folders are sourced from `TaskService.listStatusEntries`. A bound folder with missing/unreadable status receives one actionable `Task status integrity: ...` line with its integrity reason, directing the worker not to execute and the primary to inspect and repair the status. The folder value may be shortened to fit the 2048-byte cap; the repair instruction is retained. Healthy task briefs label integrity-failing dependencies with `status_missing` or `status_unreadable` instead of `unknown`.

Only native `task()` (v1) or `subagent()` (v2) dispatches whose agent resolves to base `forager-worker` (built-in or custom variant) **and** whose route snapshot has an explicitly selected feature (`selected: true`) are eligible. Fallback and explicit-null routes get neither brief nor notice. The binding is the authored assignment's first non-empty line, trimmed: `Hive task: <task-folder>` for a task listed for that feature. On v2 a continuation whose follow-up opens with no marker is bound to the task the child's stored binding names. After the unchanged route-snapshot block (v1) or the authored prompt (v2, where the route travels in the session instruction entry), a bound dispatch receives a generated block bounded by `<!-- hive-task-brief:start -->`, `## Hive task brief`, and `<!-- hive-task-brief:end -->`, at most 2048 UTF-8 bytes:

- A framing line, then `Task: <folder> - <plan title> (<status>)`; long titles end in `...`.
- `Spec: <abs path> - specStale: <v> (<reason>)` is always present; use `freshness_unavailable` when freshness cannot be computed.
- `Plan: <abs path>[ lines a-b]` is omitted if `plan.md` is missing.
- `Plan sync <state>: <hint>` appears when the feature's [plan sync status](#plan-sync-status) is not `current`. Unowned-heading line numbers after the task's section follow when present.
- `Handoff: <abs path>` appears when this task has a successor handoff.
- `Dependencies:` lists `- <folder> (<status>)[ handoff: <abs path>]` entries from the task record's `dependsOn`, with `unknown` for unknown folders, or `Dependencies: none`.
- `Feature context: <n> durable catalog entries; read with hive_context_read({ feature: "<feature>", view: "catalog" }).` gives the durable count (`unknown` when it cannot be read) and the exact catalog call. `Execution decisions: <abs path>` follows when that file exists. No document bodies are included.

To fit the budget, trailing dependency entries are dropped with `- (+<k> more; see hive_status)`. If still too long, retain core lines plus the plan-sync, unowned-heading, and handoff lines, then core lines alone; never cut a path. When locators cannot fit, the result is `Hive task brief unavailable: locators exceed 2048 bytes.` An eligible unbound dispatch gets one line under the heading: `No Hive task binding: ...` (missing/invalid marker or unknown folder); composition errors give `Hive task brief unavailable: <message>`. On each task dispatch, only generated blocks (a start marker immediately followed by its heading line) are replaced, for any agent; marker text quoted elsewhere in an authored assignment is preserved. Reviewers, scouts, advisors, and helpers never receive a brief. For task-scoped review, the primary supplies feature/task identity, plan path and current section, spec path, and current `specStale`/`specStaleReason` from `hive_status`; reviewers may query status with the explicit feature to clarify current state.

### Child session association

The same first non-empty line also associates the child session with its assignment, for any agent, so viewers can show which task or run a session works on. `Hive task: <task-folder>` sets `taskFolder` on the child's session record when the parent explicitly selected a feature that has that task; a detected or sole live feature never qualifies. `Hive run: <runId>` sets `adHocRunId` when an ad-hoc run with that ID has a worktree in this project; a run on a foreign `sourceDirectory` is not associated.

The record is written only when the host reports the actual child of that dispatch: on v1 from the `task` call's own events, on v2 at the barrier that binds the child before its prompt. Nothing is guessed from the route, the directory or the prose. The marker is exact-case. Each dispatch to a child rewrites the association from its own line:

- On v1, a resolved line replaces the association and clears the other kind. On v2, it sets the association on a fresh call or adopts one when a continued child has none, and refuses a continuation naming another task or run.
- On a fresh call, a missing line, or a line Hive cannot resolve (including `Hive task: ` followed only by whitespace), binds no task or run.
- A continuation without a line keeps the task or run the child is already bound to. On v1 an exception applies: when the captured route's effective feature differs from the child's binding, including a move to or from a featureless route, the old association is cleared, because v1 cannot refuse that continuation.
- A continuation with a line Hive cannot resolve clears the association on v1 and is refused on v2. On v2 a resolved line that names another task or run than the child's binding is also refused; see [V2 subagent dispatch and continuation](#v2-subagent-dispatch-and-continuation).

`hive_background_status` reports each child's `scope` (`feature`, `task`, `adHocRunId`) from this binding, so a child shows the route and association its latest dispatch wrote, never the parent's later route.

When the binding write fails, Hive logs a `[hive:routing]` warning naming the child, and whether the failed write changed the store is unknown. On v2 a child already bound to the captured route still runs when only that write fails; a new child or a route change still needs its binding written and fails unprompted without it. On v1 a failed write never stopped the task call, and still does not. Stores stay per host owner (`opencode-v1` or `opencode-v2`), and `lastActiveAt` is a recorded timestamp, not evidence that the session is still running.

## Snapshot

`hive_git_snapshot` is a low-level diagnostic. Inputs are optional `directory`, `repositoryIds`, `baseRef`, `targetRef`, `range`, `paths`, `maxFiles`, and `maxPatchBytes`. `directory` must be an absolute exact Git top-level and cannot be combined with `repositoryIds`; `repositoryIds` requires a manifest. It returns a `hive-git-snapshot/v1` envelope: `{ schema, status: 'ready', consistency: 'validated', snapshots: [{ repositoryId, snapshot }] }`, or `{ schema, status: 'failed', consistency: 'failed', failures: [{ repositoryId?, code, phase, retry, message }] }`. Capture is bracketed by a generation check that fails with `SOURCE_DRIFT`. One 15-second operation deadline covers the whole capture.

Each snapshot has `repository`, `scope`, `consistency`, `limits`, `changedPaths` (comparison, staged, unstaged, untracked), `fingerprint`, `patch`, and `omissions` (counts by changed-path group, patch truncation/omitted bytes, and per-section captured/returned/omitted bytes and reason). Error codes are `INVALID_REQUEST`, `UNSAFE_REPOSITORY_STATE`, `INCOMPLETE_UNTRACKED_CAPTURE`, `OUTPUT_LIMIT_EXCEEDED`, `OPERATION_TIMEOUT`, `SOURCE_DRIFT`, `INTERNAL_ERROR`, `missing-ref`, `merge-base-unavailable`, `output-truncated`, and `timeout`. Phases are `validation`, `ref-resolution`, `preflight`, `capture`, `untracked-capture`, `revalidation`, or `serialization`; retry values are `fresh-capture`, `narrow-scope`, `operator-action`, or `not-retryable`. `maxFiles` defaults to 100 (cap 200); `maxPatchBytes` defaults to 64 KiB (cap 256 KiB). Supplied limits above the caps are clamped. At most 32 repositories can be captured in one call. A composite snapshot set is all-or-error.

`/dash-review`, `/test-audit`, and `/vuln-review` are ordinary orchestrators over natural folders, inline text, or the current checkout. `/test-audit` limits the review to test quality in its named scope. Optional snapshot `directory` and an ad-hoc worktree cover a foreign PR or ref.

## Feature Resolution

Feature-scoped tools resolve in this order: explicit `feature` or `name`, selected session route (including null), detected feature worktree/path, then the sole live feature. A feature whose `feature.json` cannot be read, or whose name matches more than one feature directory, is skipped when finding the sole live feature, so one healthy live sibling still resolves. Selecting that feature with `hive_feature_select`, or naming it to `hive_status`, `hive_feature_complete` or a feature constraint tool, fails. Plan, task and context tools do not apply this check yet. The same effective route is captured for child dispatch. An explicit target wins only for that call and never changes the selected route. Explicit null suppresses detected-context and sole-live fallback. Without a resolved feature, a feature-required tool throws an error asking for `hive_feature_select` or an explicit feature. If no live feature exists, create one with `hive_feature_create`.

## Reserved Overview Convention

- There is no dedicated overview write tool.
- Use `hive_context_read({ feature: "feature-name", name: "overview" })` through all returned chunks first, then pass the current revision and `file.contentHash` to `hive_context_write`.
- Humans review `context/overview.md` first for purpose and design; `plan.md` stays authoritative for execution and task parsing, and the feature Worklog carries progress and history.
- Read the overview with `hive_context_read`; the VS Code extension also surfaces it for human review. `hive_status` returns feature and task summaries without overview content.
